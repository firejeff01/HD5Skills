# 架構健檢 improve-architecture（淺模組掃描＋HTML 報告＋質詢深挖）

> **適用對象**：主對話；使用者要求角色分工或平行掃描時，可派 sa／實作代理或唯讀探索子代理協助走讀。
> **啟動方式**：🔴 **僅由使用者啟動**（說「架構健檢」「掃架構」「improve architecture」）。
> 這是 codebase 健康度活動，**不掛在任何案子流程上**，任何代理不得自行啟動；質詢閘對本工作流不適用（不派案子角色鏈）。
> （守衛：無（是否由使用者啟動，只能從對話判斷））
> 方法論源自 Matt Pocock 的 improve-codebase-architecture skill；質詢輪走 `hd5-grill` 格式，產物沉澱走專案的 CONTEXT.md／ADR。

專案的術語檔（CONTEXT.md）與 ADR 目錄位置、報告放哪裡，見該 repo 的 `AGENTS.md`；沒寫就用 repo 根的 `CONTEXT.md`、`docs/adr/`、`reports/`。

## 一、這支 skill 解什麼問題

找出 codebase 的**架構摩擦點**——讓「淺模組」變「深模組」的重構機會，提升可測試性與 AI 可導航性。
它只負責**找到候選項＋把選定項質詢到可動工**；拍板後的重構本身走正常流程（開案子走 `hd5-workflow`，或使用者直接派發）。

### 詞彙表（用這些詞、不要漂移）

| 詞 | 定義 |
|---|---|
| **深模組** | 介面簡單、實作吸收了大量複雜度的模組（好） |
| **淺模組** | 介面複雜度≈實作複雜度，包一層但沒吸收複雜度（摩擦源） |
| **接縫（seam）** | 模組間可獨立替換／測試的邊界 |
| **位置性（locality）** | 理解一個概念所需的程式碼是否集中在一處 |
| **槓桿（leverage）** | 一次改動在多少呼叫端產生效益 |

首次使用時把上表術語（含本專案的在地化譯名）補進專案的 CONTEXT.md。

## 二、執行流程

### 步驟 1：探索（找摩擦點）

1. **範圍界定（預設 git 熱點）**：`git log` 近期改動檔案定熱點，從熱點有機往外走讀；
   使用者啟動時若指定模組／目錄，以指定範圍覆蓋預設。**不做全量掃描**。
2. **先讀沉澱檔**：專案的 CONTEXT.md（用既定術語描述發現）與 ADR 目錄
   （🔴 **已有 ADR 的決定不得當成摩擦點重提**，除非有真實摩擦證據——實際被該決定卡住的具體事實）。
   （守衛：無（有沒有真實摩擦證據、是否在重提 ADR，屬內容判斷））
3. **五類摩擦點**（可派唯讀探索子代理分頭走讀）：
   - 理解單一概念要在多個小模組之間跳躍（位置性差）
   - 淺模組：介面複雜度≈實作複雜度
   - 跨接縫的緊耦合（改 A 必動 B，但 A、B 隔著模組邊界）
   - 從現有介面難以測試（或根本沒測）的區塊
   - 純轉手函式鏈（每層只是換個名字往下傳）
4. **刪除測試**：對每個疑似淺模組問「把它刪掉、複雜度會收斂到哪裡？」——
   若刪掉後複雜度自然併入鄰居且介面變簡單，就是有效候選項。

### 步驟 2：HTML 報告

- 位置：`reports/architecture-review-{YYYYMMDD}.html`（或 AGENTS.md 指定的報告目錄），產出後開給使用者看。
- 🔴 **不依賴任何外部資源**（CDN 的樣式庫、圖表庫、字型都不用——離線或內網環境會靜默空白）；（守衛：無（產出前自查有沒有 http 開頭的 src／href；專案有自己的檢查腳本就寫在 AGENTS.md））
  手寫 inline CSS，圖用 inline SVG。產出後自查：報告裡沒有任何 `http://`／`https://` 開頭的 `src`／`href`（專案有檢查工具就用它，exit 0 才交付）。
- 每個候選項一張卡片：
  - **Files**：涉及檔案／模組
  - **Problem**：目前的架構摩擦（用第一節詞彙描述）
  - **Solution**：改動的純文字敘述（🔴 此階段**不做介面設計**，留給步驟 3）（守衛：無（卡片內容是否混入介面設計、推薦強度是否合理，屬內容判斷））
  - **Benefits**：以位置性／槓桿說明，含測試面改善
  - **Before / After**：並排結構示意（inline SVG）
  - **推薦強度**：`Strong`／`Worth exploring`／`Speculative` 三級徽章
- 報告結尾必附 **Top recommendation**：最優先候選項與理由。

### 步驟 3：質詢深挖（使用者選定候選項後）

- 對選定候選項進入質詢輪，**沿用 `hd5-grill` 的格式與鐵律**（批次輪、先查證後提問、選擇題化、三態終止、一次一題問使用者）。
  質詢對象：約束條件、依賴方向、深化後的模組形狀、介面背後收什麼、既有測試存活性。
- 質詢紀錄寫 `reports/grill-arch-{候選項}.md`（非案子產物，不進 `AI_Service/spec/`）。
- 質詢中拍板的術語**當場**落專案的 CONTEXT.md。
- 使用者**拒絕**候選項且理由值得記錄（`hd5-grill` 的 ADR 門檻）時，提議記成 ADR `NNNN-{slug}.md`（由使用者拍板才寫）——
  拒絕的理由往往比接受更值得記。

## 三、鐵則

1. 🔴 純規劃不寫碼：本 skill 全程不改任何程式；動工走正常案子流程（`hd5-workflow`）。（守衛：無（架構健檢不掛案子流程，沒有可掛閘的時點判斷它有沒有改程式））
2. 🔴 不重新討論已記錄的 ADR 決定（除非附真實摩擦證據）。（守衛：無（是否在重提 ADR 決定、證據算不算真實，屬內容判斷））
3. 🔴 步驟 2 不提介面設計，只講問題與方向；介面形狀是步驟 3 質詢輪的產物。（守衛：無（步驟 2 有沒有談介面形狀屬內容判斷））
4. 建議答案≠定案：質詢輪未拍板的一律標 `[待確認]`（比照 `hd5-grill`）。

相關：`hd5-grill`（質詢格式、ADR 門檻）、`hd5-workflow`（拍板後怎麼開案）、`hd5-no-hallucination`（先查證後提問）。
