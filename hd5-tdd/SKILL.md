# HD5 TDD 紅綠燈紀律

> 適用：實作代理（`.claude/workflow.json` 的 implementers，預設 backend-expert／frontend-expert）、qa-expert。
> 預設 TDD 模式。本 skill 與專案其他測試規範衝突時，**以本 skill 為準**。
> 本 skill 只講方法；建置、跑單支測試、跑本案範圍、前端關卡等**指令**寫在該 repo 的 `AGENTS.md`，下文用「單支測試指令」「本案範圍指令」稱呼。

## 一、角色分工

| 階段 | 負責角色 | 行為 |
|---|---|---|
| 計畫 | qa-expert（可與實作代理的計畫書並行） | 測試計畫書；待決題交主對話彙整（`hd5-workflow`「多代理計畫回合」） |
| Red | qa-expert | 依 SA 規格寫一筆會失敗的測試，交付 Red 證據 |
| Green | 實作代理 | 寫**最小**實作讓測試轉綠 |
| Refactor | 實作代理＋qa-expert | 重構保持綠燈，QA 不得擴充測試追實作 |
| Mutation | qa-expert | 隨機破壞產品程式，驗證測試會失敗 |
| 驗證與報告 | qa-expert | 核對每個情境、跑本案範圍、測試報告 |

派發順序因此是 **QA（計畫＋Red）→ 實作（Green）→ QA（驗證與報告）**，跟 `hd5-workflow`「作業順序」同一套；QA 在實作前後各派一次。

## 二、Red Gate（實作代理寫產品程式前必檢）

開始撰寫任何產品程式之前：

1. 確認 `AI_Service/spec/<案名>/qa/{功能名稱}-tdd-log.md` 中已存在對應 Scenario 的 **Red 證據**
2. 紅燈失敗類型必須是 **斷言失敗（assertion failure）** 或 **方法不存在／尚未實作**，**不可是環境錯誤**（連不上、設定缺漏、空參照、編譯環境壞掉…）
3. 若 Red Gate 不通過（沒測試、立即綠、紅燈是環境錯誤），**立即停止實作**，回報 QA 重新交付

> 若使用者要求「跳過 Red Gate 直接寫程式」，必須在開發計畫書中明確記錄「本次跳過 TDD」並請使用者書面同意，否則不得執行。

## 三、最小實作原則（實作代理）

- 只寫足夠讓**當前紅燈測試**轉綠的最小程式碼
- **不**預先實作下一個尚未紅燈的測試所需邏輯
- **不**新增測試未涵蓋的 helper／抽象層／例外處理
- 若實作中發現需要額外規則，回報使用者由 QA 增補測試，不自行擴張

## 四、Green Gate（實作代理完成必檢）

完成最小實作後：

1. 先建置一次，再用**單支測試指令**（不重複建置）跑新測試，確認**全綠**
2. 跑 **L2**（見第十二節）確認**本案範圍未退化**：本案完整範圍的測試＋前端完整關卡（有動前端時）。
   🔴 **會寫共用資料的測試不准跑**——專案若有「全套會碰共用資料庫／共用環境」的測試，AGENTS.md 會寫明怎麼排除；跨案退化由合併前的 L2 與 CI 兜底。（守衛：無（哪些測試會寫共用資料由各專案的 AGENTS.md 定義並自設守衛））
3. 將綠燈輸出貼到 `qa/{功能名稱}-tdd-log.md` 對應 Scenario 的 **Green 證據** 區塊
4. 任一條件不滿足都不算完工

## 五、QA 寫 Red 測試的規範

1. 依規格寫**最小**測試一筆，斷言**業務狀態**（不是 mock 呼叫次數）
2. 用單支測試指令執行，**必須失敗**
3. 失敗類型必須是斷言失敗或方法不存在，**不可是空參照等環境錯誤**
4. 若立即綠或拋環境錯誤，視為**假紅燈**必須重寫
5. 將紅燈輸出貼進 `qa/{功能名稱}-tdd-log.md` 作為交付證據

### 受測元件／模組還不存在時，什麼算合格的 Red

新功能常常連受測的元件、模組、類別都還沒有。這時「找不到」本身可能是**尚未實作**，也可能是**環境壞了**（路徑打錯、建置沒跑、測試工具載不到檔），兩者看起來很像。合格的 Red 要同時滿足：

1. **失敗類型是斷言**：測試自己判斷「受測對象不存在／沒有這個行為」並以斷言失敗報出來，不是讓載入、編譯、匯入錯誤直接把整支測試炸掉。
   （怎麼做依技術而定，例如先用執行期查詢取得受測對象、取不到就斷言失敗；具體寫法由專案寫進 AGENTS.md 或測試規範。）
2. **失敗訊息預先寫好**：斷言訊息在寫測試時就定好（例：「尚未實作：找不到 X」），Red 證據裡出現的就是這句；出現的是別的錯誤＝不是你以為的那個紅。
3. **證明環境沒壞**：同一支測試檔裡另有一支走**不同路徑**的測試（例：測既有元件、或只檢查測試工具本身能載入）同時正常執行——
   它照預期通過或照預期失敗，代表檔案有被收進母體、工具與環境是好的，紅燈才能歸因於「尚未實作」。
4. 實作完成後，同一支測試不改任何一行就轉綠（Green Gate 照第四節）。

### 特徵化測試（實作前本來就綠）不算 Red

有些測試在實作前本來就該是綠的：鎖住**不能變**的既有行為（不變性）、或證明**不該發生**的事（反例：「沒有實質資料的項目照舊不顯示」「舊入口照舊能用」）。這叫特徵化測試：

- 它**不算 Red 證據**，不能拿來過 Red Gate；Red Gate 要的是對應新行為、而且真的會紅的那幾支。
- 它跟第九節反模式 10「測試先綠燈才開始」的差別在於**有沒有證明它會抓錯**：反模式是「本來就綠、也沒人證明它有在驗東西」；
  特徵化測試必須在 tdd-log 另列一區「特徵化測試」，每支附 **mutation 證據**——故意把它守護的行為改壞（第六節做法），它要紅；還原後要綠。
- 沒有 mutation 證據的「本來就綠」測試，一律當反模式 10 處理（重寫或刪掉）。

## 六、Mutation 自我驗證（QA 強制執行）

每組新測試交付前必須執行 mutation check：

1. 在產品程式隨機破壞一行（反轉布林、改常數、刪一行）
2. 跑測試，**必須有測試因此失敗**
3. 若所有測試仍綠 → 該測試是假的，必須重寫斷言
4. 將 mutation 結果寫入 `qa/{功能名稱}-tdd-log.md`
5. 還原破壞後要**重新建置**，確認跑的是還原後的產物（產物時間或雜湊要新於還原動作），才可以接著用「不重複建置」的方式跑測試

**守衛也要 mutation**：故意違規一次，確認該守衛會紅。沒有反例驗證的守衛等於沒有守衛。

## 七、資料存取層測試一律用真的資料庫

| 項目 | 規定 |
|---|---|
| 資料存取層（Repository 等）測試 | 用**與正式環境同一種**資料庫引擎的本機或容器實例（真實查詢行為） |
| 禁止 | 用記憶體模擬資料庫或另一種引擎代替——重現不了空值與布林的處理、排序規則（collation）、日期時間精度、唯一索引等差異 |
| 連線設定 | 從測試專用設定檔載入，每個測試類別自帶 fixture 建立／拆毀 schema；**不可連共用資料庫** |
| 資料初始化 | 真的 `INSERT` 或經由正式的寫入路徑寫入 |

服務層測試仍可 mock 資料存取介面，但**斷言必須驗證業務狀態**（回傳的成功與否／訊息／實體欄位值），**不可只斷言 mock 被呼叫**。

> 教訓：曾有測試環境的設定跟正式環境不同（測試裡寫入會自動生效、正式環境不會），把「匯入後沒寫回」這個正式環境才會出的錯遮掉很久。
> 測試環境的設定要跟正式環境一致，至少要有一支測試走跟正式環境相同的設定。

## 八、測試保護（實作代理強制禁止）

- **嚴禁修改 QA 撰寫的測試斷言或測試資料**讓測試變綠
- 嚴禁註解、停用、跳過（各框架的 skip／ignore 標記）QA 寫的測試
- 嚴禁刪除 QA 寫的測試檔案
- 若認為測試本身有誤（例如規格被測錯），必須回報使用者由 QA 修正，實作代理不得自行動測試

## 九、假測試反模式（出現任一項即視為假測試，必須重寫）

| # | 反模式 | 為什麼是假的 |
|---|---|---|
| 1 | 只斷言「結果不是空的」或「成功＝true」，沒驗證資料正確性 | 任何不丟例外的實作都會通過 |
| 2 | 服務層測試只驗證「mock 的更新方法被呼叫一次」 | 沒驗證業務規則本身 |
| 3 | 資料存取層測試用記憶體模擬資料庫 | 與真實資料庫行為不符 |
| 4 | Mock 被測類別本身 | 被測對象必須是真實物件 |
| 5 | 吞掉例外後無條件判通過，或沒有斷言的測試 | 永遠通過 |
| 6 | 測試名稱描述「實作做了什麼」而非「規格要求什麼」 | 測試在描述實作 |
| 7 | 同一測試方法跑多個 Scenario | 失敗時無法定位 |
| 8 | Mutation check 全綠通過 | 測試對產品程式變化無感 |
| 9 | Happy path only，缺異常／邊界 | 規格涵蓋不足 |
| 10 | 測試先綠燈才開始（沒經過紅燈），又沒有 mutation 證據 | 無法證明測試確實在驗證新邏輯；特徵化測試要附 mutation 證據才不算（第五節） |
| 11 | 測試吃的是產品程式的**複製品**（把要測的程式碼抄一份到測試裡改） | 複製品不會反映真實迴歸；測試要吃出貨的原始碼 |
| 12 | 用模擬環境推論它模擬不了的行為（例：用無瀏覽器的 DOM 模擬推論真瀏覽器、真外掛的行為） | 模擬環境的差異會讓真實失效靜默通過；這類行為要用真實元件的行為測試或端對端測試 |

## 十、TDD 交付清單格式

每筆測試的 `qa/{功能名稱}-tdd-log.md` 必須包含：

```md
## TDD 交付：{Scenario 名稱}

### Red 證據
- 測試：{完整名稱（含命名空間／檔案路徑）}
- 執行指令：{單支測試指令，照 AGENTS.md}
- 失敗輸出（節錄）：
  ```
  {貼上紅燈的斷言訊息或 stack trace}
  ```

### Green 證據（實作完成後填寫）
- 實作檔案＋行號：
- 執行指令：
- 通過輸出：

### Mutation 驗證
- 破壞點：{檔案:行號，描述破壞動作}
- 預期失敗測試：{測試完整名稱}
- 實際結果：{ pass / fail }
- 還原 commit／動作：
```

## 十一、Refactor 階段紀律

綠燈後可重構產品程式，但：

- 每次儲存都必須跑測試保持綠燈（L0；每輪結束跑 L1，見第十二節）
- 重構不得改變測試斷言能觀察到的行為
- 若重構導致任何測試變紅，**立即回滾或修正實作**（不是改測試）

## 十二、什麼時候跑什麼（分層跑法）

| 層 | 時機 | 跑什麼 |
|---|---|---|
| 免跑 | 只動文件／spec／需求文件／純資料腳本（照該類規範另外驗） | 不跑測試 |
| L0 | Red／Green／Refactor 每次存檔 | 建置一次 → 只跑正在寫的那個測試類別／檔案（不重複建置） |
| L1 | 每輪複驗、commit 前 | 本案所有測試範圍**合成一次呼叫跑完**＋與改動檔相關的前端測試＋型別檢查＋守衛 |
| L2 | Green Gate、合併前、送獨立審查（hd5-review）前 | 本案完整範圍＋前端完整關卡；同一台機器同時只准一個 session 跑 |

- 多數測試執行器每叫一次都有固定開銷（探索整個測試組件／啟動環境，跟選幾支無關）⇒
  **少叫幾次比少選幾支有效**；每次都重新建置會再多付一次建置確認。
- L1 只為了省時間，可以多跑、不可漏跑；漏跑由 L2 兜底，L2 不能省。

### 🔴 先驗測試母體：「全綠」可能只是「少跑」（守衛：無（各專案依測試框架自建母體比對腳本，名稱寫進 AGENTS.md））

篩選條件（filter／pattern）對不到任何測試時，多數執行器**不會報錯**，只會安靜地少跑。
曾有一組例行篩選長期「全綠」，其實有二十個測試（含一支真的違反契約的）從沒被收進母體。

- 新增或沿用別人的篩選條件時，**先驗母體**：解析**實跑結果檔**（JUnit XML、TRX 之類，依框架而定）裡實際執行的測試類別／檔案，
  對上磁碟上實際的測試類別／檔案數，並確認沒有混進該排除的類別。
- **「列出測試」類的指令不可信**——曾有同一篩選條件列出近三百筆、實跑不到五十筆。以實跑結果為準。
- 前端測試執行器同樣會**靜默少收測試檔**：每次比對執行器報告的檔案數 vs 磁碟上的測試檔數。
- 篩選字串含 `&`、`|` 等字元經過殼層（shell）包裝時可能被切斷、排除子句失效——確認有引號包住。
- 「數字很大而且全綠」不代表覆蓋到，可能只是**沒收到**。

### 🔴 黃金基準（快照／對照）測試要確認基準不是自己（守衛：無（基準來源是否正確要人判斷））

若基準是用「新版」擷取的，等於新版跟自己比，必然全綠。重建基準時必須用**改動前的舊版**產生，並找一個只有舊版才會有、新版一定沒有的特徵做健檢。

相關：hd5-verify（回報口徑、像使用者一樣驗證）、hd5-review（送審時附 tdd-log 與實跑結果檔）、hd5-workflow（流程總綱）。
