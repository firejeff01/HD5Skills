HD5Skills · 使用者導入手冊

把 AI 協作開發流程裝進你的專案

HD5Skills 是一套跟程式語言無關的 AI 工作流程。裝好之後，Claude Code 或 Codex 接到需求時會照固定步驟走：先問清楚、再設計、再寫程式和測試、最後像使用者一樣實際操作驗收。你要做的事只剩回答問題和拍板。

這是什麼優點導入前準備怎麼導入 日常怎麼用整體流程注意事項之後更新常見問題 → Skills 地圖

01這是什麼

AI 寫程式最常出問題的地方通常不在程式本身。它會在需求沒問清楚時自己腦補，「測試全綠」實際上是少跑了，或是說做完了，其實從沒打開畫面點過。HD5Skills 把這些地方變成一定要過的關卡，其中幾個關卡是真的會擋人的程式（hook 與檢查腳本），不只是文字提醒。

它分成兩層：

流程（套件提供，所有專案共用）

案子怎麼分路線、要派哪些角色、每個階段過什麼關卡、怎麼回報、怎麼結案。這一層跟你用什麼語言、什麼框架無關。

專案事實（導入時掃描產生，每個專案自己的）

你的專案怎麼建置、怎麼跑測試、哪些測試不能亂跑、分支怎麼命名、有哪些容易踩的坑。這些寫在專案自己的 AGENTS.md。

Claude Code 和 Codex 讀同一份 AGENTS.md，所以兩邊的規則不會各寫各的。

02優點

不腦補

文件沒寫的事，AI 會列成選擇題問你，每題附建議答案，不會自己猜一個做下去。

派專人做專事

需求交給 PM、設計交給 SA、程式交給實作代理、測試交給 QA。主對話不直接改產品程式，有 hook 擋。

先紅再綠

QA 先交一份會失敗的測試，實作讓它轉綠，之後再故意改壞程式，確認測試抓得到。看不到紅燈的測試不算數。

像使用者一樣驗

每個功能都有一份「功能地圖」，寫清楚從哪裡進去、按什麼、成功長怎樣。驗收要實際操作到最終結果，並留下證據。

第三方把關

開發完成後，交給沒參與開發的 Codex 或全新的子代理唯讀審查，只修會擋人的問題，不無限輪迴。

回報不灌水

每一條主張都要對得上實際跑過的結果，用「已驗證／已完成未驗證／受阻」三種狀態回報，沒驗到的會直接說。效能數字要說得出瓶頸在哪、排除量錯的可能，才算數。

先想好程式的形狀

SA 設計時先定資料形狀、外部輸入在哪裡檢查、重跑會不會出錯，重要的決定列 2～3 個方案並排給你選。實作先刪再加、遷移完不留舊 API，審查者也會看這些。

上線後的錯也算帳

正式環境才發現的缺陷，會記回當初交付它的案子，跟驗收退回一起統計。哪一關一直漏，數字會說話。

密碼不會跟著程式出去

送審前自動掃描新增的程式有沒有寫死密碼、金鑰、權杖，也附上套件弱點掃描結果，有問題先修才送審。

同一個錯不犯第二次

錯第二次就做成會擋人的檢查。每條 🔴 紅燈規則都要標明是由哪個守衛在擋，對帳工具會檢查。

換技術也能用

.NET、Node、Python、前後端分離或單一層都適用。工具一律讀 .claude/workflow.json，不寫死資料夾和副檔名。

04怎麼導入（三步）

  1. 跑安裝腳本，把 skills 和工具放進專案

    開一個 PowerShell 7（pwsh）視窗，在裡面用 & 直接執行（路徑換成你的）：

    # 專案就在 repo 根目錄
& D:\HIRC-DMZ\AI_Service_Agent\HD5Skills\install.ps1 -RepoRoot D:\work\MyRepo

# Claude Code 是在 repo 的子資料夾啟動（例：repo 裡的 src\MyApp）
& ...\HD5Skills\install.ps1 -RepoRoot D:\work\MyRepo -ProjectDir src\MyApp

# 有用 Azure DevOps 工單，要一起裝工單工具
& ...\HD5Skills\install.ps1 -RepoRoot D:\work\MyRepo -Tracker azure-devops

    -ProjectDir 是「你會在哪個資料夾打開 Claude Code」，相對於 repo 根目錄。在 repo 根目錄打開就不用給。

    裝完會自動跑幾支測試，確認 hook 能動。已經存在的檔案不會被覆蓋。

  2. 在專案資料夾打開 Claude Code，請它導入

    直接說：導入工作流，或輸入 /hd5-onboard。Codex 也一樣，說「導入工作流」就好。

    AI 會掃描整個專案（語言、框架、建置和測試指令、CI、目錄分層、既有的 CLAUDE.md／AGENTS.md），再挑代表性的程式讀懂架構。它不會讀 appsettings、.env 這類含密碼的檔案。

  3. 回答問題、看報告、決定要不要 commit

    掃描推不出來的事，AI 會一題一題用選擇題問你，每題都附建議答案。第一題一定是分支怎麼命名：開發分支、工作分支前綴、測試和正式分支，以及 AI 可以 push 哪些。其他常見題目：

    • 測試怎麼跑才安全（有沒有測試會寫到共用資料庫）
    • 完整測試要跑多久，平常怎麼縮小範圍
    • 規格文件的正本放哪裡
    • 怎麼部署、用什麼工單系統、哪些動作一定要人決定

    從既有文件就查得到答案的題目，AI 會整批列給你一次確認，不會每題都問。

    問完之後 AI 會產生下面這些檔案，再用檢查腳本把關，最後給你一份報告：改了哪些檔、架構摘要、還有哪些「🟨 待補」。AI 不會自己 commit，看過 git diff 覺得可以，再自己 commit。

導入後專案裡會多出什麼

位置是什麼誰維護
AGENTS.md主檔：這個專案的技術架構、建置和測試指令、環境陷阱、協作規則。Claude 和 Codex 都讀專案（你可以改）

AI_Service/onboard/agent-base/代理範本的基準：記住上次同步的是哪一版範本，-Update 靠它分辨哪些小節是你改的。要進版控，不要手改套件（-Update 維護）

既有專案和新專案的差別

專案原本就有 CLAUDE.md／AGENTS.md／代理

原檔會先備份，新舊差異給你看，你同意後才覆蓋。原本的每一條規則都會記在去向表（rules-migration.md），標明搬到哪、留在哪，或為什麼不搬。原本的代理名稱（例 csharp-expert）會保留成過渡期別名，進行中的案子不會壞。

全新或沒有 AI 設定的專案

AI 會從 README、docs、交接紀錄裡找「一律／不可／禁止／必須」這類規則，整理成既有規則清單。功能地圖只建它讀程式說得出操作步驟的功能，說不出的列成「待建」，不放空殼。

05日常怎麼用

導入完成後不用記指令，用平常說話的方式交代就好。AI 會照流程判斷要用哪個 skill。

你想做的事可以這樣說會發生什麼
開一張新案子幫我處理這張工單 <網址>我要做一個…功能讀工單建案、判定路線、照路線派角色
修一個小 bug這個按鈕按了沒反應，幫我修走「小問題」路線：先派 SA 盤查原因和同類位置，再派實作
正式環境出 bug正式站這個功能壞了，是 #123 做的一樣走小問題路線，SA 會標「逃逸：是，來源 #123」；結案時記回 #123 的退回總帳，看得出是哪一關漏掉
需求還很模糊grill 我質詢這份設計把待決事項攤成決策樹，附建議答案一輪一輪問到全部拍板
實際點點看功能實際驗一下這個功能照功能地圖開系統、操作到最終結果、截圖存證
開發完要審查送獨立驗收交給沒參與開發的第三方唯讀審查，總結「通過／不通過／受阻」
部署到測試站後上站驗一下站上關卡先確認站上跑的是這一版，再逐條操作驗收項目
收尾交接寫結案報告產生固定 8 節的結案報告，有工單系統時掛到工單
改工單狀態改成待驗收在工單留言改狀態前自動檢查證據齊不齊；留言內容會先給你看
套件更新後代理有衝突更新代理逐節合併代理檔裡你和套件都改過的小節，給你看差異、你同意才寫入
評估要不要重構架構健檢產出候選重構點的 HTML 報告；只規劃，不寫程式

你主要的工作就是拍板。AI 遇到要你決定的事，會用選擇題一題一題問，並標出建議選項。push、改工單、發通知、部署正式環境、寫共用資料這些對外動作，都會先給你看，你同意才做。

06整體流程

每張案子建立時，AI 會先判定它走哪條路線，並寫在案子的 spec_001.md。沒寫路線，後面派人的關卡就不放行。

四角色

新功能、需求模糊、資料模型或權限變動、跨前後端

PM → SA → QA（Red）→ 實作 → QA

PM 端已完成

需求方已經用 PM agent 產出需求文件

檢查 PM 產物 → SA → QA（Red）→ 實作 → QA

小問題

沒有需求文件的小問題、緊急 bug

SA 盤查（bug-analysis.md）→ QA（Red）→ 實作 → QA

高風險的案子（資料模型、權限、跨模組、正式資料修正）會在 SA 之後多一輪「對抗輪」：另派一個全新的代理，專門挑 SA 設計的錯，處理完才開始寫程式。

一張案子從頭到尾

起點主對話

讀工單或需求、建案資料夾、判定路線和高風險。

你：確認路線
需求PM

分析需求、寫驗收條件，接著自動進質詢輪，把沒講清楚的地方問到拍板。體驗優先：除了正常路徑，也寫出載入中、沒資料、失敗時使用者看到什麼；功能太多又趕時，會問你先做哪幾項、每項做到多完整。

你：回答質詢題
設計SA

掃描專案、做技術設計，同樣自動進質詢輪。設計質詢多一個「設計形狀」分支：資料形狀、領域規則放哪、外部輸入在哪裡檢查、重跑會不會出錯、有沒有共用狀態、要重新設計還是接上去；重要的決定列 2～3 個方案並排比較（SA 紀錄沒有這一節，派實作前質詢閘會印警告）。高風險案子接著跑對抗輪。

質詢閘：派 SA／實作／QA 前檢查
實作實作代理

QA 先交一份會失敗的測試 → 實作讓它轉綠 → 重構 → 用 mutation 確認測試抓得到錯。修 bug 前先列出所有同類的位置。寫程式照代理檔的「程式設計原則」：先刪再加、檢查放在系統邊界、加防護不等於修好、遷移完同一波刪掉舊 API。每完成一條驗收條件，就照功能地圖自己驗一次。

主對話改檔 hook：主對話不准直接改產品程式功能地圖檢查
測試QA

對照每個情境讀測試程式、出測試報告、檢查資安。

審查第三方

沒參與開發的 Codex 或全新子代理唯讀審查整案，除了驗收項目和證據，也看設計品質（防護有沒有蓋住根本原因、舊 API 或相容層有沒有留著）。只修 P0／P1，P2 以下列為已知限制。

獨立驗收：通過才能合併
上站主對話

合併、部署到測試環境，然後逐條在站上操作到最終結果、留證據。

站上關卡：通過才能送驗收你：同意 push／部署
結案主對話

寫結案報告（固定 8 節，給下一張工單參考）。改工單狀態前會自動檢查：獨立驗收過了沒、站上關卡過了沒、每個 Pass 都有證據嗎。

工單閘你：同意改工單、發通知

紅框是會擋人的程式關卡，綠框是需要你決定的地方。每個關卡的細節見 Skills 地圖。

07注意事項

密碼和權杖 AI 一律不碰。AI 不讀密碼檔、不代打密碼、不幫你設 PAT（存取權杖）。用 Azure DevOps 工單工具時，PAT 請自己放進環境變數或本機 PAT 檔（已被 .gitignore 排除）；自架的 Azure DevOps Server 在 Windows 上沒設 PAT 時，會改用目前登入的帳號驗證。

會寫共用資料的測試一定要講。如果專案有測試會連到大家共用的資料庫，導入時問「測試怎麼跑才安全」那題請照實回答。AI 會把安全的跑法寫進 AGENTS.md，之後只照那個方式跑。

導入時

  • 導入產出的檔案要進版控。如果 .gitignore 忽略了 AGENTS.md、CLAUDE.md 或 .claude/，檢查腳本會擋下，並告訴你是哪個 .gitignore 的第幾行。拿掉之後要通知同事：他們電腦上如果有自己的同名檔，pull 會被擋，要先改名或刪掉。
  • 在子資料夾啟動時，規則可能疊兩份。Codex 會從 repo 根目錄一路讀每一層的 AGENTS.md，Claude 也會讀上層的 CLAUDE.md。AI 會建議把 repo 根目錄那份縮成一行轉向，改之前會先問你。另外也檢查一下，自己電腦上有沒有沒進版控的個人 AGENTS.md／CLAUDE.md，有的話裡面的舊規則會跟新的衝突。
  • 導入後請人看一遍 AGENTS.md。它是之後 AI 的規則來源。標「🟨 待補」的是 AI 問了你也答不出來的事，之後知道了再補。
  • 代理檔裡的關鍵規則不能只寫「見某份文件」。子代理實測很少主動去讀 skills，重要規則要直接寫在 .claude/agents/ 的本文裡。

日常使用

  • Codex 沒有 hook。Claude 會被 hook 自動擋，Codex 只能靠紀律：派角色之前要自己跑一次質詢閘（validate-grill-gate.ps1）。這條 AGENTS.md 裡會寫明。
  • 真的要主對話直接改程式時，在案子的 spec_001.md 寫一行「主對話直接改：理由（使用者 MM-DD 同意）」，hook 就會放行。
  • 新增 🔴 規則時要標守衛。格式是「（守衛：守衛名稱）」，沒有守衛就寫「無（理由）」。對帳工具 check-guard-refs.mjs 會擋沒標的規則。
  • 防毒或沙箱軟體可能影響 hook。有些端點防護（例 COMODO）會把程式寫出的檔案隔離，造成「檔案明明在卻說不存在」或測試偶發失敗。遇到時先懷疑環境，不要急著改套件。所以安裝要在已開的 PowerShell 7 視窗裡用 & ...\install.ps1 執行，不要用 pwsh -File install.ps1 另開程序；裝完到專案資料夾確認 .claude/skills/hd5-workflow 真的在。hook 範本也已改用 pwsh -Command 執行。根本解法是請 IT 把開發用資料夾或 pwsh、node 設為排除。

08之後怎麼更新套件

母版出新版時，在已經導入過的專案跑：

& ...\HD5Skills\install.ps1 -RepoRoot D:\work\MyRepo [-ProjectDir src\MyApp] -Update

會更新

hd5-* skills（Claude 和 Codex 兩份）、AI_Service/hd5-tools/ 底下的工具。有用 Azure DevOps 時，工單工具也一起更新。

代理檔逐節比對

.claude/agents/ 以小節為單位比對三份：上次同步的範本、新範本、你現在的檔。你沒改過的節自動換新版，範本新加的節自動補上，「本專案技術架構重點」永遠不動。

不會動

AGENTS.md、CLAUDE.md、workflow.json、settings.json、案子和功能地圖、你的 PAT 檔。

不會刪

套件已經不含的舊檔只會列出來，由你確認要不要刪。

你和套件都改過的小節，交給 AI 合併。這種小節（或第一次三方比對、還沒有基準時內容不同的小節）-Update 不會動，會列在 AI_Service/onboard/agent-update.md，每節附三個版本。在專案啟動 Claude Code 說「更新代理」，AI 會保留你的調整、採用套件的新規則，矛盾的地方問你；你同意才寫入。某個代理合併完，再跑一次：

& ...\HD5Skills\install.ps1 -RepoRoot D:\work\MyRepo [-ProjectDir src\MyApp] -Update -AcceptAgents sa-expert

它把那個代理的基準設成目前範本，下次就不再列衝突。實作代理靠 workflow.json 的 gateRole（backend／frontend）對到範本，其他 gateRole 只提醒、不比對。

-Update 不能跟 -Force 一起用。-Force 會把代理和 workflow.json 也覆蓋回範本，等於把導入時調好的內容洗掉，除非你確定要重來，否則不要用。

09常見問題

導入要多久？

安裝腳本只要幾分鐘。掃描和問答依專案大小與既有文件多寡而定：沒有既有 AI 設定的小專案很快；規則很多的大型既有專案（要整理每一條規則的去向）會花比較久，大部分時間在等你回答問題。

我的專案不是 .NET，可以用嗎？

可以。流程跟技術無關，技術細節由掃描產生。實作代理的數量和分工也依你的架構決定：只有一層就只有一個實作代理，也可以另外加（例 mobile-expert）。

沒有用工單系統可以嗎？

可以。安裝時不給 -Tracker 就不裝工單工具，案子直接用你的描述建立。之後要接 Azure DevOps，再用 -Tracker azure-devops 重跑一次安裝。

小改動也要走完整流程嗎？

不用。小問題走「小問題」路線：SA 盤查完就派實作。純文件或工具的修改，主對話可以自己做。但寫程式還是要派實作代理，不能因為「自己做比較快」就跳過。

AI 會自己 push 或部署嗎？

不會，除非你在導入時明確授權（例如「開發分支驗證後可以直接 push」）。授權的範圍寫在 AGENTS.md。正式環境一律由人處理。

導入的結果不滿意怎麼辦？

AI 不會自己 commit，用 git diff 看完，不要的直接還原就好。被覆蓋的原檔在 AI_Service/onboard/backup/，每條舊規則去了哪裡都記在 rules-migration.md。
