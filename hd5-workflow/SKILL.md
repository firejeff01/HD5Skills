# HD5 AI 協作開發流程

本 skill 只講**流程**。專案的技術架構、建置與測試指令、環境陷阱寫在該 repo 的 `AGENTS.md`（Claude 經由 `CLAUDE.md` 的 `@AGENTS.md` 讀到）；
實作代理有哪些、各管哪些檔，寫在 `.claude/workflow.json`。還沒有這些檔的 repo，先用 `hd5-onboard` 掃描產生。

## 角色

| 角色 | 代理 | 做什麼 |
|---|---|---|
| 主對話 | （你） | 建案、判路線、照路線派代理、把待拍板題一題一題問使用者、併分支、站上關卡、結案。**不直接改產品程式** |
| PM | pm-expert | 需求分析、驗收條件、質詢輪 |
| SA | sa-expert | 掃專案、技術設計；小問題路線改做盤查，寫 `sa/bug-analysis.md` |
| 實作 | `.claude/workflow.json` 的 implementers（預設 backend-expert／frontend-expert） | TDD＋驗紅；先列同類位置再修 |
| QA | qa-expert | 實作前：測試計畫＋Red 證據（`hd5-tdd` Red Gate）；實作後：讀測試碼核對每個情境、mutation、測試報告、資安 |
| 獨立審查者 | 沒參與開發的第三方（Codex，或全新子代理，不可 fork） | 看整案 diff 與行為證據 |

**作業順序**（三條路線共用，與 `hd5-tdd` 第一、二節一致）：
PM → SA →（高風險：對抗輪）→ **QA（測試計畫＋Red）→ 實作（Green）→ QA（驗證與報告）**。
實作代理寫產品程式前要看到 QA 交的 Red 證據（Red Gate），所以 QA 會被派兩次；計畫書可以並行出（見「多代理計畫回合」），但 Red 一定在實作之前。
做不了自動化測試的改動（純文件、純設定），在計畫書寫明「本次跳過 TDD」並取得使用者同意（`hd5-tdd` 第二節）。

角色定義只有一份：`.claude/agents/<角色>.md`。**Codex 擔任某角色時**（Codex 沒有子代理），完整讀該檔本文照做，忽略 frontmatter 的 tools／model；
專案自有、放在 `.claude/skills/<名>/` 的 skill，Codex 直接讀該 `SKILL.md`。專案的 AGENTS.md 要寫明這一條（check-onboard 沒看到會警告）。

## 案件路線（建案時判定，必須寫下來）

建案完成時在 `AI_Service/spec/<案名>/case_spec_content/spec_001.md` 文末加一行：
`路線：<四角色｜PM 端已完成｜小問題>，高風險：<是｜否>，外部系統：<有｜無>，理由：…`

外部系統＝抓對方網頁、呼叫對方 API、讀對方產的檔案；「有」⇒ SA 要列 `sa/external-samples.md` 樣本對照表（`hd5-grill` 第三節第九分支）。
「外部系統：」也可以另起一行寫；沒寫時質詢閘印警告（不擋，見「關卡」表下的說明）。

| 路線 | 什麼時候 | 怎麼派 |
|---|---|---|
| 四角色 | 新功能／需求模糊／資料模型或權限變動／跨前後端 | pm → sa → qa（計畫＋Red）→ 實作 → qa（驗證與報告）全派 |
| PM 端已完成 | 需求方已用 pm agent 產出需求文件 | 主對話檢查 pm 產物（沒答的題一題一題問；每份 `spec_*_r*.html` 要有對應的 `*_answer*.html`）→ 從 sa 開始派，之後同四角色 |
| 小問題 | 沒有需求文件的小問題／緊急 bug | 先派 sa 盤查，寫 `sa/bug-analysis.md`（原因／影響範圍／同類位置／修法／待決事項）→ qa（Red）→ 實作 → qa；緊急也要 SA 文件寫完才派 |

- **高風險**（資料模型／權限／跨模組／正式資料修正）：SA 之後、派實作前，另派全新子代理專門推翻 SA 結論（對抗輪），結果寫 `sa/adversarial-review.md`，處理完才往下。
- **不要因為「自己做比較快」就不派。** 主對話自己做只剩純文件／工具修改；做到一半範圍變大就停下改路線並告知使用者。
- 派發的 prompt 一定寫案子路徑 `AI_Service/spec/<案名>`、完成條件（指令＋期望值）、熔斷（同一指令連紅三次、工具呼叫 100 次就停）。
- **守護主對話的上下文**：大量讀取（全專案搜尋、長 log、整份資料表、大型 diff）交給子代理或唯讀探索子代理，主對話只收摘要與檔:行，不貼原始內容。

## 開工檢查（每個 session 第一次派代理之前）

- 🔴 **可派的代理清單要含 `.claude/workflow.json` 的 implementers**（以及 pm／sa／qa-expert）。沒有＝這個 session 不是在專案資料夾啟動
  （例：專案在 repo 子目錄，卻從 repo 根開）：專案代理與 hook 都沒載入，而且**沒有任何訊號**——skills 照樣讀得到，直到派代理才暴露，
  hook（質詢閘、主對話改檔守衛）整段沒生效。**停下來請使用者在專案資料夾重新啟動**；事後 `cd` 進去不會補載。
  專案在子目錄時可選配 repo 根的 SessionStart 警告，見 `hd5-onboard` 第 4 步。（守衛：無（session 載入了哪些代理只有主對話看得到））
- 派發 hook 每次放行都會回一行「grill-gate 放行：…」；派角色代理後沒看到這行＝hook 沒載入，同上處理。

## 多代理計畫回合（多個代理並行出計畫書時）

實作代理與 QA 常並行出計畫書，各自帶回待決題，而且彼此重複（同一題被兩方獨立提出）。逐題照轉會爆量，由主對話先彙整：

1. **彙整去重**：各計畫書的待決題收成一張表（題目、提出者、影響哪份計畫），同一題合併。
2. **分流**：
   - **需人拍板**：需求語意、驗收方法、寫共用資料、對外動作、會推翻上游拍板的題。
   - **主對話可定**：已有專案慣例（AGENTS.md、ADR、既有程式寫法）或被禁令限定、只剩一個合法選項的題——寫出依據（慣例／禁令出處）與理由，註明使用者可推翻。
3. **寫裁定檔** `pg/decisions-{主題}.md`：每題一列 `| # | 題目 | 提出者 | 分類（需人拍板／主對話定） | 裁定 | 依據／理由 |`。
4. **需人拍板的一題一題問**（附選項與建議），答案回填裁定檔。
5. **一次「確認開始」**：裁定檔與各計畫書一起給使用者，使用者確認一次才往下（QA 寫 Red → 實作）；之後的派發 prompt 寫明裁定檔路徑，各代理照裁定修計畫、不再重問。

## 關卡（會擋人的檢查）

| 關卡 | 什麼時候 | 工具（`AI_Service/hd5-tools/`） |
|---|---|---|
| 質詢閘 | 派 sa／實作／qa 前 | `validate-grill-gate.ps1`：沒寫路線 8、有路線又跳步 9、小問題缺 SA 分析 10、高風險缺對抗輪或沒標高風險 11、質詢紀錄 2～4、功能地圖 5～7、派實作／QA 前 grill 紀錄還有待拍板題 12、PM 端已完成但 `spec_*_r*.html` 沒有對應 answer 13。另印警告（不擋）：沒寫「外部系統：有｜無」、外部系統＝有但 `sa/external-samples.md` 缺或樣本不齊、`qa/rework-log.md` 有「新規則」退回但 grill 沒有收斂完的「驗收回合 R{k}」小節 |
| 派發 hook（Claude） | 每次派子代理 | `hooks/grill-gate.ps1`：prompt 指到案子就呼叫質詢閘；放行時也回一行「grill-gate 放行：走哪條路徑、代理、案子、閘 exit 碼」 |
| 主對話改檔 hook（Claude） | 主對話每次 Edit／Write | `hooks/main-edit-guard.ps1`：有進行中案子時，主對話改產品程式就擋（例外：spec_001 寫「主對話直接改：理由（使用者 MM-DD 同意）」）；建議派誰依 workflow.json 的 `roleHints`（例 tests/ 歸 qa-expert）→ 實作代理 `pathHints` → 副檔名；`productCode.excludeDirs` 只比前綴、`**/` 才比任意層 |
| 功能地圖 | 開工、站上關卡 | `verify-map-check.ps1`：每個功能怎麼到達、怎麼操作、地雷；Pass 要有證據 |
| 獨立驗收 | 實作與 QA 完成後、合併前 | 結果檔最後一行 `總結：通過｜不通過（P0 n／P1 n／P2 n）｜受阻（缺 X）`；只修 P1（含 P0）；受阻補齊後重送同一輪 R{n}b |
| 站上關卡 | 部署到測試環境後 | A 表驗收項目逐條操作到最終結果＋證據；B 表平台契約（由專案定義）；`總結：通過｜不通過｜受阻`。`verify-map-check.ps1 -Onsite`（工單閘同一套）另印警告（不擋）：退回後沒有（新打通）列或「新打通：無（理由）」、同一項連兩輪「未驗證（待使用者動作）」又沒有「使用者放行：…（MM-DD）」 |
| 守衛對帳 | 每次跑守衛 | `check-guard-refs.mjs`：每條紅燈規則要標守衛欄；做不到的列進專案的 guard-backlog |
| 退回紀錄 | 改待驗收、改驗收完成、驗收完成後上傳結案報告（工單閘自動跑）；也可手動 `--check` | `check-rework-ledger.mjs`：工單歷程退回 k 次 ⇒ `qa/rework-log.md` 記滿 k 輪；驗收完成 ⇒ 結案報告 5.1 列數＝rework-log 列數（0 次寫「退回 0 次」）、總帳有本案同樣列數；總帳格式、根因類別、對應規則欄、程式寫法類的守衛與待辦只在 verify（`--check`）紅，工單閘用 `--gate` 不擋 |

> Codex 沒有 hook：Codex 派發前要**顯式**跑 `validate-grill-gate.ps1`，主對話不改產品程式靠紀律，事後用指標檢查。

> **只警告、不擋的檢查**（2026-11-25 使用者拍板）：外部系統宣告與樣本表、驗收回合質詢、退回後的新打通、待使用者動作連兩輪。
> 這些管的是需求溝通與人工步驟，程式碰不到內容對不對，擋了容易被湊數敷衍或繞過；真正的防線在產品程式層（樣本契約測試、新規則的自動化測試、端到端回歸測試）。
> 質詢閘的警告是 stdout 的「grill-gate 警告：…」（派發 hook 帶進放行訊息）；站上關卡的是「⚠ 站上關卡警告（不擋）：…」。看到就處理或跟使用者說明，不要略過。

## 錯誤升級階梯

糾正一次就變成確定性檢查（Lauren Tan）。落點由上往下選：產品程式架構（型別／API／目錄邊界，讓錯的寫法寫不出來）→ 靜態檢查（棘輪、lint、架構測試）→ 自動化驗證（測試）→ 流程閘 → 文字（最後手段）。
- 🔴 **驗收退回的根因是程式寫法類**（樣本不足／修後沒重跑／測試資料形狀／動作順序／其他）**第一次就做程式守衛**：總帳 `AI_Service/spec/rework-ledger.md` 那一列的「對應規則」要寫測試類別、`guard:xxx`、棘輪或架構檢查；
  做不到先列 `待辦（G-NN）`（進 guard-backlog），同類再犯時待辦還沒做成守衛就紅。無（理由）、流程閘、文字都不算。需求類（規則定義晚／新需求／缺證據或使用者動作）才可寫 `無（理由）`。
  這條只讓開發端 `check-rework-ledger.mjs --check`（verify）變紅，不擋工單結案（`hd5-case-report` 第七節）。（守衛：check-rework-ledger.mjs）
- 做守衛時，**既有的同類寫法預設提案一起清**；棘輪基準（先凍結現有數量、只准減）只是過渡，不是終點。
新增或修改 🔴 規則時一定標「守衛」標記（寫守衛名稱、無（理由）或專案 guard-backlog 的待辦編號）。（守衛：check-guard-refs.mjs）

## 對外動作由人決定

push、改工單、發通知、部署正式環境、寫共用資料：先讓使用者看、使用者同意才做。不代打密碼、不設存取權杖。

## 收尾

QA 驗證與報告完成 → 獨立驗收通過 → 合併 → 部署測試環境 → 站上關卡通過 → 結案報告（固定 8 節）→ 改工單狀態前工單閘自動檢查（有工單系統時）
→ 需求方最終驗收通過 → 結案報告補第 5.1 節退回檢討＋記跨案子退回總帳（`hd5-case-report` 第七節）。

## 驗收退回之後

需求方退回時，先把退回內容逐條分類，再決定怎麼往下走：

| 類別 | 例子 | 怎麼處理 |
|---|---|---|
| 程式錯誤 | 某種資料讀不到、畫面沒顯示原因 | 照原路線修（先列同類位置）→ 獨立驗收 → 站上關卡；**修好後被打通的後段流程本輪要驗**（`hd5-onsite-gate` 第四節；站上關卡只警告不擋，長期由自動化端到端回歸測試取代） |
| 新規則／重新定義概念 | 「改過就算手動資料」「只有值變了才算修改」 | **先補質詢再寫程式**（`hd5-grill` 第二節第 6 條；質詢閘只警告不擋）：查欄位實際何時被寫入 → 用選擇題逐項請需求方勾 → 寫進 grill 紀錄 → 才派實作。其中屬程式寫法的部分（例：拿修改人欄位推論「改過」）照「錯誤升級階梯」做程式守衛 |
| 缺證據／缺使用者動作 | 夜間實跑紀錄、開機自動啟動 | 下一輪送驗前補齊；要使用者動手的先問使用者，做不到就在留言寫明「這項還不能驗」 |

🔴 每輪退回都記進案子的 `qa/rework-log.md`，一列一條原因：`| 輪次 | 退回原因 | 處理類別 | 根因類別 | 錯誤寫法 | 為什麼開發端沒先抓到 | 修正 |`
（輪次寫 `R1`、`R2`…，可接日期，同一輪多條原因就多列；處理類別用上表；根因類別用 `hd5-case-report` 第七節的固定清單；錯誤寫法＝一句話寫出錯的程式寫法長什麼樣，需求類可寫 `不是程式寫法（理由）`）。
下一次改「待驗收」時工單閘會數工單歷程退回幾次（State 變成 `tracker.rejectedStates`，預設「驗收未過」），rework-log 記的輪數不夠就擋。（守衛：check-rework-ledger.mjs）
🔴 需求方最終驗收通過時，結案報告補第 5.1 節「退回檢討」（一列對 rework-log 一列；沒退回寫「退回 0 次」），並把每次退回記進專案層的跨案子退回總帳 `AI_Service/spec/rework-ledger.md`（`hd5-case-report` 第七節）。
改「驗收完成」、驗收完成後上傳結案報告時工單閘會對 rework-log、5.1、總帳三方列數。（守衛：check-rework-ledger.mjs）
