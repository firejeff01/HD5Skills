# HD5 獨立驗收（有 Codex 用 Codex，沒有改用 Claude）

> 適用：主對話。實作完成後、合併／部署測試環境之前必跑。審查者**不是**開發中的這個對話本身。
> 緣由：開發完要先給「沒參與開發的第三方」看過程式。很多人只有 Claude ⇒
> **電腦有 Codex 就用 Codex，沒有就派一個全新的 Claude 子代理**，兩條路共用同一份委託檔、同一種結果格式，
> 後續流程（只修 P1、站上關卡、改待驗收）都不用分辨是誰審的。

---

## 一、在流程中的位置

```
實作＋QA 完成 → 【獨立驗收】→ 只修 P1（修完再送一輪）→ 合併 → 部署測試環境 → 站上關卡 → 通知需求方
```

- P2 以下列已知限制交需求方，不在這個循環裡修。
- 站上關卡見 hd5-onsite-gate。獨立驗收看程式，站上關卡看測試環境上的結果，兩個都要。

## 二、先判斷用誰（每一輪都判斷，不要沿用上次的結論）

依序檢查，**三項都過才用 Codex**，任一項不過就用 Claude：

| # | 檢查 | 指令 | 不過的情況 |
|---|---|---|---|
| 1 | 有安裝 | PowerShell `Get-Command codex -ErrorAction SilentlyContinue`；bash `command -v codex` | 沒有輸出 |
| 2 | 有登入 | `codex login status` | 不是 `Logged in …` |
| 3 | 跑得起來 | 實際執行第四節 A 的指令 | 沙箱初始化失敗、持續滿載、版本異常、逾時 |

- 第 3 項失敗時**不要反覆盲試，也不要要求放寬沙箱**，直接改用 Claude，並在結果檔開頭寫「Codex 無法執行：{錯誤摘要}，改由 Claude 審查」。
- 回報時講清楚這一輪是誰審的。

## 三、委託檔：`qa/獨立驗收委託_R{n}.md`

放在 `AI_Service/spec/<案名>/qa/`。`{n}` 從 1 開始，每送一輪加 1（受阻重送用 `R{n}b`，見第五節）。

委託檔要能讓**完全沒看過這個對話**的審查者獨立完成，固定包含：

```markdown
# {案號} {一句話主題}——獨立驗收委託 R{n}

你是獨立審查者。請以**唯讀**方式審查，用繁體中文輸出結果。

## 限制
- 唯讀：不改檔、不 commit、不連資料庫、不開服務、不呼叫外部 LLM。不要讀含密碼／金鑰的設定檔（哪些檔見 AGENTS.md）。
  不要跑會寫共用資料的測試（範圍見 AGENTS.md）。

## 範圍
- repo：{worktree 絕對路徑}，分支 {branch}
- 受驗 diff：`git diff {起點}..{終點} -- {路徑}`
- 規格／驗收基準：{需求文件、答覆紀錄、質詢拍板紀錄（grill-*.md）路徑}
- 上一輪委託與結果（R2 起）：{路徑}

## 本輪修正（R2 起）
- R{n-1}-NN（P1）：改了什麼、怎麼驗的（含反向驗證：拿掉修正時哪支測試紅）

## 行為證據（實作階段產出；只列路徑與「它證明什麼」，不寫結論）
- 測試：`qa/{功能}-tdd-log.md`（Red／Green／mutation）、實跑結果檔：{路徑}（實際執行的測試類別／檔案數＝{n}）
- 畫面（有 UI 改動時必附）：截圖／錄影 {路徑}——對應驗收項 {AC-x}；有雛形時附並排圖
- 守衛結果：守衛彙總（{n}/{n}）、本案新增或觸動的守衛／ratchet 名稱
- 開發中自驗（照 `AI_Service/verify/` 功能地圖操作）：`pg/verify/` 證據清單——每條對應 {AC-x}｜{功能編號}
- 沒有證據的驗收項：列出來（審查者據此標「未驗證」，不要用讀碼推定通過）

## 請審查
1. 是否符合規格的每一條驗收項目
2. 上一輪缺陷是否確實消除（R2 起）
3. 有無引入新缺陷、有無漏掉同類位置（所有呼叫點／所有語系列／所有入口）
4. 「行為證據」是否真的證明它宣稱的事（截圖對得上驗收項、實跑結果檔的母體對得上測試類別、mutation 有紅）；
   證據與程式碼矛盾時以程式碼為準並列為缺陷

輸出：總結、判定表、缺陷清單（`R{n}-NN`｜等級｜檔:行｜問題｜推理｜建議｜證據等級）、未驗證項目。
結尾兩行固定（順序不可反）：
新發現：{編號 一句話}／0 筆
總結：通過｜總結：不通過（P0 n／P1 n／P2 n）｜總結：受阻（缺 X）
```

🔴 委託檔**只寫事實與範圍，不寫開發者的結論**（例如「這個應該沒問題」）——給了結論，審查者容易照單全收。（守衛：無（委託內容是否夾帶開發者結論屬語意判斷））

📸 **證據前移**（參考 Lauren Tan「審查看證據」）：畫面類證據在實作階段就要產出，並隨委託檔交給審查者，
而不是等站上關卡才第一次看畫面。審查者的工作從「讀碼推定」擴大到「核對證據是否成立」。證據標準見 hd5-verify 第四節。

## 四、執行

**跑之前**先記下受驗 worktree 的狀態，跑完再比一次，確認審查者沒改檔：

```bash
git -C "<worktree>" rev-parse HEAD
git -C "<worktree>" status --porcelain --untracked-files=all | md5sum
git -C "<worktree>" diff | md5sum
git -C "<worktree>" ls-files --others --exclude-standard -z | (cd "<worktree>" && xargs -0 -r md5sum) | md5sum
```

- 🔴 **一定要 `--untracked-files=all`**：案子資料夾（spec、證據、tdd-log）常常整個是 untracked，預設的 `status --porcelain`
  對整個資料夾只印一行 `?? <資料夾>/`，審查者在裡面新增、刪除、改檔，這行都不變——雜湊對證據檔是盲的（試跑實例：審查前後新增了結果檔，雜湊照樣相同）。（守衛：無（這是審查前後由主對話手動比對的指令））
- `--untracked-files=all` 只看得到 untracked 檔**有沒有增減**，看不到內容改了沒有——第四行對每個 untracked 檔算內容雜湊補上。
  `diff` 只涵蓋已追蹤的檔；被 `.gitignore` 排除的檔兩者都看不到，證據放在被忽略的資料夾時要另外對那個資料夾算檔案雜湊。
- 審查者的結果檔本來就會新增（例 `qa/Codex驗收結果_R{n}.md`）：比對時先排除這一個檔，其他任何差異都要查。

### A. 用 Codex

```bash
codex exec -s read-only -C "<worktree>" -o "<qa 目錄>/Codex驗收結果_R{n}.md" - < "<qa 目錄>/獨立驗收委託_R{n}.md"
```

- 背景執行一定要從檔案餵 stdin（上面的 `- < 委託檔`），否則會卡在「Reading additional input from stdin」。
- 審查需要建置或跑指定測試時，才改用 `-s workspace-write`，跑完一樣比對雜湊。
- 逾時中斷後可能殘留 Codex 的子程序：先用親子關係確認是自己這次開的，再連同子程序一起結束（只殺自己開的）。

### B. 用 Claude

派一個**全新**的子代理（`general-purpose`，**不要用 fork**——fork 會帶著開發脈絡，就不獨立了）：

- prompt＝委託檔全文（或「請完整讀取 `<委託檔路徑>` 並照做」），另外加一句：
  「把完整結果寫到 `<qa 目錄>/Claude驗收結果_R{n}.md`，最後一行照委託檔規定的格式。」
- 不要在 prompt 裡補充開發過程、也不要轉述你認為的修正理由；需要的資訊都應該已經在委託檔裡。
- 子代理回來後，主對話**自己讀結果檔**確認最後一行，不要只看子代理的回報摘要。

## 五、結果檔與判讀

| 審查者 | 結果檔 |
|---|---|
| Codex | `qa/Codex驗收結果_R{n}.md` |
| Claude | `qa/Claude驗收結果_R{n}.md` |

🔴 **檔名就是契約**：工單閘等自動檢查只認 `qa/` **根目錄**的 `{Codex|Claude}驗收結果_[中綴_]R{n}.md`
（中綴可放案號、工作包，例 `Codex驗收結果_123_R10.md`；受阻重送 `…_R{n}b.md`）。
子目錄（`qa/codex/`）、`.raw.md`、「第三輪」這類中文輪次都**不認**。原始輸出要留就留，但正式結果一定另存成上述檔名。（守衛：無（各專案的工單閘照此檔名規則判讀；沒有工單閘的專案靠主對話紀律））

- 最後一行是 `總結：通過` ⇒ 進下一步（合併）。
- `總結：不通過（P0 n／P1 n／P2 n）` ⇒ 只修 P1（P0 當然也修），修完寫 R{n+1} 委託再送；P2 以下列已知限制。
- `總結：受阻（缺 X）` ⇒ 證據不足以判定（例：委託沒附行為證據、審查者跑不起來指令、實跑結果檔對不上母體）。
  補齊 X 後重送**同一輪** `R{n}b`（再受阻就 `R{n}c`），**不算一次不通過**；工單閘不放行受阻。
  🔴 不要把「證據不夠」寫成不通過，也不要寫成通過：前者多跑一輪修正，後者是沒驗到卻放行。（守衛：無（證據是否足以判定屬審查者判斷））
- 結果檔裡 `新發現：` 在倒數第二行、`總結：` 永遠是最後一行（hd5-verify 8.4）。
- 跑前後雜湊不一致 ⇒ 這一輪作廢：先查審查者改了什麼、還原，再重跑。
- 後續文件（站上關卡、改待驗收前檢查）說「獨立驗收通過」，指的是上表結果檔**最新一輪**的總結行為 `總結：通過`，
  或 `總結：不通過` 但 P0、P1 都是 0（只剩 P2＝已知限制）。自動判定取檔內**最後一個** `總結：` 行。

## 六、常見誤區

| 誤區 | 正確 |
|---|---|
| 「我自己再看一遍」當成獨立驗收 | 開發中的對話不算；要 Codex 或全新子代理 |
| 用 fork 子代理審查 | fork 帶著整段開發脈絡，不獨立；用 `general-purpose` |
| 委託檔或 prompt 裡寫「這個應該沒問題」「修正理由是…」 | 只給事實、範圍、證據路徑 |
| Codex 壞了就一直重試 | 判斷第 3 項不過，直接改 Claude，結果檔寫明原因 |
| 只看子代理的回報摘要就說通過 | 主對話自己讀結果檔最後一行 |
| 上一輪用 Codex，這一輪就假設還能用 | 每一輪都重新判斷 |
| P2 也一起修 | 只修 P1（含 P0），P2 以下列已知限制 |
| 證據不夠就判不通過（或通過） | 判受阻（缺 X），補齊後重送 R{n}b |
