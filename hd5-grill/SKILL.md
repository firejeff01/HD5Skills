# hd5-grill：需求／設計質詢（決策樹拍板法）

> 適用對象：全角色（pm／sa／實作代理／qa）
> 啟動方式：**pm-expert／sa-expert 強制自動執行（各自 checkpoint 後一律質詢，不可跳過）**；實作代理／qa 僅由使用者啟動（見第二節）
> 方法論源自 Matt Pocock 的 grill-me skill（規劃期質詢、純規劃不寫碼），
> 依實戰經驗改造：批次輪取代一次一題、強制先查證、與 Open Questions HTML（`hd5-spec-html`）管道縫合。
> 專案的技術細節（唯讀資料庫怎麼查、權限模型、語系機制）不在這裡，見本專案 `AGENTS.md`。

## 一、這支 skill 解什麼問題

顆粒度缺口實測分三類，**各有各的解法，本 skill 的質詢只直接命中第一類**——
但質詢過程要負責把另外兩類「分流」到正確的管道，不可用文字質詢硬蓋：

| 缺口類型 | 特徵 | 典型例子 | 解法 |
|---|---|---|---|
| **裁決類** | 文件有寫大方向，但值域／口徑／預設值／衝突處理沒定 | 「匯入重複列要自動去重還是擋下」拖到第六輪才拍板；某個狀態欄位為 NULL 時算哪一類沒人定 | **本 skill 質詢**（第二～三節） |
| **看見才知道類** | 利害關係人要看到真畫面才會有意見 | 「日期選擇器顯示成別的語言」「下拉預設落到第一筆」到驗收才退回 | 質詢中標記【需雛型】→ PM 階段產低成本 HTML mock，不要用文字問 |
| **資料現實類** | 答案藏在資料庫真實資料裡，文件與利害關係人腦中都沒有 | 「某個語系設定其實是隱藏的資料開關」；「現有資料裡某狀態欄位有幾十列是 0、幾十列是 NULL」 | 質詢前**先實查**（第三節鐵律 2）；「舊資料相容」分支必須以實查結果作答 |

## 二、觸發與範圍閘

1. 🔴 **PM 階段強制執行**：pm-expert 於階段二（PM Gherkin）完成後
   **必須自動進入質詢輪**——不需使用者啟動、不得詢問使用者「要不要質詢」、也不得跳過。
   需求質詢是 PM 產出的必要組成：需求層的裁決若在 PM 階段沒拍板，成本會以數倍放大轉嫁到
   SA／實作／QA。範圍閘對 PM **不適用**（一律執行）；case 很小時決策樹自然短——
   與本 case 無關的分支明寫「N/A－理由」即可，質詢輪不會因此變重。（守衛：validate-grill-gate.ps1）
2. 🔴 **SA 階段強制執行**：sa-expert 於階段一（專案掃描）完成後、
   寫 `sa/*.feature` 之前**必須自動進入設計質詢輪**——不需使用者啟動、不得詢問使用者
   「要不要質詢」、也不得跳過。SA 之後就直接進實作：設計層的裁決
   （架構選型、介面契約、權限與語系的資料閘、舊資料相容）若在 SA 階段沒拍板，會原封不動變成實作代理的
   實作假設。範圍閘對 SA **不適用**（一律執行）；case 很小時決策樹自然短——與本 case
   無關的分支明寫「N/A－理由」即可。**「舊資料相容」分支必須先以唯讀資料庫實查作答**。（守衛：validate-grill-gate.ps1）
3. **實作代理／qa 僅由使用者啟動**（說「grill 我」「質詢這份設計／計畫」），或 agent 於
   第五節所列 checkpoint **建議使用者啟動**。**這些角色不得自行開始質詢輪**——實作／測試層
   的質詢會拉長對話、而且答案的權威在使用者，這個成本要由使用者決定花不花。
4. **範圍閘**（僅適用實作代理／qa 的建議門檻）：新模組／跨模組改動／資料模型、權限、
   多語系變動；前端另有「大型元件」門檻（新元件 >1 支，或元件與後端／母頁之間的資料契約含互動狀態）。
   小 bug 修、單點文案改**不建議啟動**（成本不划算），走 `hd5-no-hallucination` 的問題清單即可。
5. 質詢輪**只做規劃、不寫任何程式碼**（原版鐵律，沿用）。
6. **驗收中途冒出的新規則，先補質詢再寫程式**：需求方在退回或回覆裡給了新規則、或重新定義一個概念
   （例：「改過就算手動資料」「什麼叫已確認」），主對話要先做完三件事才派實作：
   - 用唯讀查詢或讀程式，查清楚判斷依據的欄位實際**在哪些操作下會被寫入**（不要拿「有沒有修改人／修改時間」代替「值有沒有變」）；
   - 把定義寫成選擇題（第四節格式），選項列出使用者**實際會做的操作**（例：只打開就按確定、只暫存、存檔但值沒變、只留審查意見），
     請需求方逐項勾「算／不算」；
   - 答案寫進原本的 `grill-*.md`（新增 `## 驗收回合 R{k}（MM-DD）` 小節，`R{k}` 用 `qa/rework-log.md` 的輪次，題號接續），之後才實作。
   不可以先照自己的理解做、再把邊界寫在送驗留言裡請對方「維持就不用回」——那等於把質詢延到下一輪驗收，每次都多一輪換版加覆驗。
   **工具提醒（警告、不擋）**：`qa/rework-log.md`（輪次欄寫 `R{k}（MM/DD）`、處理類別欄寫「新規則」）有新規則的列時，派實作／QA 前
   `pm/` 或 `sa/` 的 `grill-*.md` 要有標題含「驗收回合」與該輪 `R{k}` 的小節，小節內至少一個已拍板／已查證／已轉單、沒有待拍板行；
   沒有就由 `validate-grill-gate.ps1` 印「grill-gate 警告：驗收回合：…」（派發 hook 會把這行帶進放行訊息），exit 碼照舊。
   為什麼不擋：要不要補質詢、需求方怎麼答，是程式碰不到的需求溝通；擋了容易被一個空殼小節敷衍或繞過。
   真正的防線在產品程式層——新規則一定要有對應的自動化測試（`hd5-tdd`）。

## 三、質詢方法（決策樹拍板法）

1. **先攤決策樹**：把本 case 的待決分支列成樹，至少涵蓋八個標準分支——
   功能範圍／資料模型／值域與預設值／權限（含資料範圍與授權入口，專案的權限模型見 AGENTS.md）／
   多語系（含「語系是不是資料閘」）／舊資料相容／UI 行為／錯誤與邊界處理。與本 case 無關的分支明寫「N/A－理由」。
   **串接外部系統的案子（抓網頁、呼叫對方 API、讀對方產的檔案）另加第九分支「外部系統變化」**：
   先列出對方會有幾種變化（例：帳單類型、頁面版型、帳期起訖日不在月初月底、欄位有無、錯誤頁），
   每一種寫進 `sa/external-samples.md` 的樣本對照表（變化／真實樣本／誰提供／開發階段實跑結果）。
   沒有樣本的變化轉成「請提供某種樣本」的題目交需求方（測試資料由需求方準備，開發不造），
   **不能等送驗時才要**；到送驗仍沒樣本的變化，在交付留言裡列成已知風險。
   推算出來的值（例：推定的期間、預設值）碰到規則（重疊、唯一性、上下限）會怎樣，也在這個分支各寫一個情境。
   每種變化的真實樣本要變成**產品程式層的樣本契約測試**（拿樣本檔餵解析／抓取程式，驗輸出），這才是擋住「只測一種樣本」的防線；
   站上關卡不再逐種列 A 項。
   **工具提醒（警告、不擋）**：`spec_001.md` 沒寫「外部系統：有｜無」，或寫「有」但派實作／QA 前 `sa/external-samples.md` 缺檔、沒有樣本表
   （表頭含「變化」「真實樣本」欄）、一列都沒有、某列「真實樣本」空白或「待提供」沒寫誰 ⇒ `validate-grill-gate.ps1` 印「grill-gate 警告：…」，exit 碼照舊。
   為什麼不擋：對方有幾種變化、樣本誰給，是需求溝通；擋了只會換來一張湊數的表。
   **SA 的設計質詢另加第十分支「設計形狀」**（PM 寫「N/A－PM 不談設計」）。逐項回答，跟本 case 無關的寫「N/A－理由」：
   - **資料形狀**：核心型別、資料結構、狀態有哪些；不合法的狀態能不能讓它寫不出來（列舉、狀態物件、必填）；變體是否都列出來、要窮舉處理。
   - **領域規則放哪**：用結構表達（型別、規則表、狀態機），不散成各處的條件判斷；名稱對上 CONTEXT.md。
   - **邊界**：外部輸入（API、設定、檔案、外部系統）在哪一層解析成內部型別；業務邏輯能不能寫成純函式。
   - **冪等**：會寫資料的操作（匯入、排程、遷移、補資料）中斷後重跑，結果是否一樣；不一樣就寫怎麼讓它一樣。
   - **共用狀態**：有沒有多個執行者（背景工作、併發請求、多個元件）共用狀態；先找不共用的做法，確定要單一寫入者才設計鎖或佇列。
   - **重新設計還是硬接**：新需求有沒有改變既有設計的前提；有的話照「第一天就有」設計，列出要一起遷移的呼叫端與要刪的舊 API（不留相容層）。
   - **備選方案**：承重的設計決定（資料模型、對外契約、模組切分）列 2～3 個互相競爭的方案並排比較（結構示意或介面草圖），寫成題目的選項，
     不要只給一個方案請人點頭。
   這一分支的拍板結果寫進 `sa/grill-*.md`，實作代理的「程式設計原則」以它為準。
2. 🔴 **先查證後提問（鐵律）**：能從 codebase、資料庫（唯讀查詢，連線方式見 AGENTS.md）、
   既有文件（含 `spec_*_answer*.html`、`CONTEXT.md` 詞彙表、`docs/adr/` 決策記錄，見第八節）
   查到答案的**不許問**；查了要在題目的「依據」欄附證據（檔案:行號／查詢＋結果摘要）。
   查不到才有資格變成問題。
   **已有 ADR 的決策不得重問**——除非能附上「真實摩擦」證據（既有決定在本 case 實際
   造成的具體問題），否則引用該 ADR 標 `已查證` 即可。（守衛：無（ADR 是否該寫要靠判斷；可列進專案 guard-backlog 當機械化候選））
3. **批次輪**：每輪把「前置條件已齊」的題**一次列出**；答案依賴其他題的留到下一輪。
   ⚠ 這裡刻意偏離原版 grill-me 的「一次一題」——實證是兩輪 10 題全拍板，批次輪的溝通成本低得多。
   （這是質詢**產出**的組織方式；主對話把待拍板題**轉問使用者**時，仍照 `hd5-workflow`「一題一題問」。）
4. **承重優先**：影響下游最多決策的先問（例：資料模型分支通常壓在值域與 UI 之上）。
5. **每題強制附建議答案**（選擇題化）：利害關係人從「寫申論題」變成「勾選擇題」，
   回填率與速度都會提升。
6. **終止條件**：決策樹上每個分支都處於三種狀態之一——
   `已拍板`（使用者親口回答）／`已查證`（附證據）／`已轉單`（轉入 PM Open Questions
   HTML 或標【需雛型】，等非工程角色回覆）。有任何分支不在這三態，質詢未完成。

## 四、問題格式（強制）

```
Q-{編號}：{問題，一句話說清楚在決定什麼}
  ├ 選項 A：{...}
  ├ 選項 B：{...}
  ├ 建議：{A/B}——{一句話理由}
  └ 依據：{查證過什麼所以確定文件／codebase／資料庫沒有答案；引用查證證據}
```

- 編號用 Q-01、Q-02…，跨輪不重編。
- 質詢紀錄寫入 `AI_Service/spec/<案名>/<角色目錄>/grill-{主題}.md`：每題記
  `Q-XX＝{答案}（拍板人／日期）`。**下游角色必讀此檔**，位階比照 `spec_*_answer*.html`
  （已拍板項目視為定稿需求）。

## 五、各角色 checkpoint

| 角色 | 啟動方式 | checkpoint 位置 | 質詢對象 |
|---|---|---|---|
| pm-expert | 🔴 **強制自動執行**（不需使用者啟動、不得跳過） | 階段二（PM Gherkin）完成後、階段三（HTML）之前 | 需求本身：範圍、流程、值域、邊界。未決題與【需雛型】題落入階段三 Open Questions HTML（`hd5-spec-html`）。守衛：validate-grill-gate.ps1 |
| sa-expert | 🔴 **強制自動執行**（不需使用者啟動、不得跳過） | 階段一掃描完成後、寫 `sa/*.feature` 之前 | 設計決策：架構選型、前後端資料契約、權限與語系的資料閘、與既有慣例的衝突點；**「舊資料相容」分支必以資料庫實查作答**。守衛：validate-grill-gate.ps1 |
| 後端實作代理 | 使用者啟動（agent 於範圍閘內建議） | 實作計畫書的「承重假設清單」節 | 實作假設：每條要嘛附查證證據、要嘛列為 Q-XX 等拍板 |
| 前端實作代理 | 使用者啟動（agent 於大型元件門檻內建議） | 畫面改造的可行性判定之後 | 僅大型元件（新元件 >1 支或資料契約含互動狀態）：元件與母頁／後端的分工、契約欄位、比對基準來源 |
| qa-expert | 使用者啟動（agent 於範圍閘內建議） | 測試計畫書的「測試母體假設」節 | 哪些不測＋為什麼；測試母體是否對上真正的權威來源 |

（實作代理有哪些、叫什麼名字，見 `.claude/workflow.json` 的 implementers。）

## 六、與既有鐵則的關係（不可打架）

1. 🔴 **建議答案≠定案**：未拍板的題在所有產物中一律標 `[待確認]`，比照
   `hd5-no-hallucination` 第六節；**使用者親口回覆前不得清除**，
   也不得因為「建議看起來很合理」就當作已回答。（守衛：無（「使用者是否親口回覆」無法由機器從產物判定））
2. 🔴 **PM 層級的問題不代答**：判定屬 PO／BA／客戶決策的題，標 `已轉單` 轉入
   Open Questions HTML，由工程窗口以外的人回填；工程窗口（使用者）只拍工程可決的題。（守衛：無（哪些題屬 PO／BA／客戶決策是語意判斷））
3. **與 `hd5-no-hallucination` 的分工**：該 skill 管「文件**未定義**」的被動觸發；
   本 skill 管「文件**有寫但假設承重**」的主動掃描。兩者的問題格式一致（第四節），
   產物都收斂到同一份 grill 紀錄／Open Questions，不搞兩套編號。
4. **質詢紀錄是決策記錄**：驗收爭議時以 `grill-{主題}.md` 的拍板記錄為準，
   位階等同 `spec_*_answer*.html`。

## 七、機制化 gate（質詢閘）

Claude 由派發 hook（`AI_Service/hd5-tools/hooks/grill-gate.ps1`）自動呼叫；Codex 不會載入 hook，
因此第五節 checkpoint 由版控內的唯讀腳本**顯式**執行：

- **位置**：`AI_Service/hd5-tools/validate-grill-gate.ps1`。
- **規則**：派發 SA 時以 `-Role sa` 檢查 `pm/grill-*.md`；派發實作代理／QA 時以
  `-Role <實作代理的 gateRole>|qa` 檢查 `sa/grill-*.md`（gateRole 見 `.claude/workflow.json`）。
  紀錄至少要包含一個終止標記（已拍板／已查證／已轉單），否則腳本回傳非零 exit code。
- **呼叫範例**：
  `pwsh -File AI_Service/hd5-tools/validate-grill-gate.ps1 -Role sa -CasePath AI_Service/spec/<案名>`。
- **路線**：先讀 `case_spec_content/spec_001.md` 的「路線：」行（`hd5-workflow`「案件路線」）。
  沒寫 ⇒ exit 8。路線＝小問題時，`-Role sa` 不需要 `pm/`；`-Role <實作>|qa` 改查 `sa/bug-analysis*.md`
  （原因／影響範圍／同類位置／修法四節＋終止標記或「待決事項：無」，缺 ⇒ exit 10）。
  同一行要有「高風險：是｜否」（沒寫 exit 11）；高風險派實作／QA 前要有處理完的 `sa/adversarial-review*.md`（「對抗結論：」，缺 ⇒ exit 11）。
- **待拍板**（2026-11-24）：派實作／QA 前，`pm/grill-*.md`、`sa/grill-*.md` 只要還有一行「待拍板」或「[待確認]」而沒標「已轉單」、後面也沒接「已拍板／已查證」⇒ exit 12
  （本節第六節第 1 條的機械化：有終止標記≠每題都收斂）。「待拍板：無」「待拍板 0 題」這類總結行不算。
- **問卷回收**（2026-11-24）：路線＝PM 端已完成時，`pm/` 或 `case_spec_content/attachments/` 的每份 `spec_*_r*.html` 都要有同名的 `*_answer*.html`
  （放 `pm/` 或 `case_spec_content/`），缺 ⇒ exit 13。
- **警告（不擋，2026-11-25）**：下面兩項照樣檢查，但只在 stdout 印「grill-gate 警告：…」（派發 hook 帶進放行訊息），exit 碼照舊。
  - 外部系統：`spec_001.md` 該寫「外部系統：有｜無」——建議寫在路線那一行（`路線：四角色，高風險：否，外部系統：無，理由：…`），
    也可以另起一行 `外部系統：有`；寫「有」時派實作／QA 前看 `sa/external-samples.md`（第三節第 1 條第九分支）。`-SkipRoute` 時不看。
  - 驗收回合：`qa/rework-log.md` 有處理類別＝新規則的輪次 R{k} 時，派實作／QA 前看有沒有收斂完的「驗收回合 R{k}」小節（第二節第 6 條；
    小節還有待拍板題照樣被 exit 12 擋）。`-Skip` 時不看。
- **跳步**：有寫路線就不准 `-Skip`（exit 9）——三條路線都不跳步，小問題走「小問題」路線。
  只有本規則生效前已進行中的舊案可用 `-SkipRoute "理由"` 搭配 `-Skip`，並在派發 prompt 記錄 `GRILL_GATE=skip`；
  主對話與 agent 不得自行決定跳過。
- **範圍**：只有已定位到的案子（`AI_Service/spec/<案名>/`）才呼叫腳本；找不到案子或上游資料夾時不得假裝通過，
  應回報缺少的路徑。不屬於任何案子的任務不套用本 gate。

## 八、質詢產出的持久化：CONTEXT.md 與 ADR

> 方法論源自 Matt Pocock 的 grill-with-docs skill：質詢不只產生「本案」的裁決記錄，
> 還要把**跨案可重用**的術語與重大決策當場沉澱到版控檔案，讓下一個 case 的質詢輪
> 不必重新推導。`grill-{主題}.md` 與本節產物**不互相取代**——前者是本案裁決記錄
> （位階同 spec answer），後者是跨案沉澱。

### 8.1 兩個沉澱檔的位置（入版控，新 worktree 自帶）

位置以本專案 AGENTS.md 為準；沒寫就用專案資料夾（`.claude` 所在那層）底下的預設位置。

| 檔案 | 內容 | 寫入權 |
|---|---|---|
| `CONTEXT.md` | **純領域詞彙表**：術語名、一句話定義、與相近詞的區辨。不含實作細節、不含規格描述 | pm-expert／sa-expert 質詢輪＋使用者 |
| `docs/adr/NNNN-{slug}.md` | 架構決策記錄：通過三道門檻的重大決策 | **僅 sa-expert 質詢輪＋使用者手動裁示**（PM 層術語只進 CONTEXT.md，不開 ADR） |

檔案不存在就當場建立（懶建立），不要求前置基礎建設。

### 8.2 CONTEXT.md：術語當場落檔，不是最後批次整理

- 質詢輪中每當一個**領域術語**拍板（例：「盤查類別」與某個表單類型欄位是不是同一件事、
  某個畫面元件的邊界定義），**當題結束就寫入**，不要等質詢輪結束批次補。
- 鐵律：CONTEXT.md 是純詞彙表。值域、預設值、流程等裁決屬 `grill-{主題}.md`，不進來。
- 後續質詢與產出文件必須沿用 CONTEXT.md 的既定術語，不得漂移
  （不要把已定名的詞換成 "component"、"service" 之類的泛稱）。

### 8.3 ADR：三道門檻全過才寫

1. **難以反轉**：改變這個決定的成本高（資料模型、對外契約、架構分層）。
2. **背景脈絡不明顯**：三個月後的人（或另一個 agent）看程式碼推不出為什麼。
3. **有真實取捨**：確實放棄了另一個可行選項，且理由值得記下來。

大多數拍板**達不到**門檻——它們留在 `grill-{主題}.md` 就夠了。ADR 格式：
狀態／脈絡／決策／取捨（放棄了什麼、為什麼）／拍板人與日期／來源
`grill-{主題}.md` 連結。編號 NNNN 遞增不重用。

### 8.4 與查證鐵律的閉環

- 第三節鐵律 2 的查證來源**包含** CONTEXT.md 與 `docs/adr/`：質詢輪開場先讀這兩處，
  已決定的不重問（重問須附「真實摩擦」證據）、已定名的不重新命名。
- 這就是 retrospective 迴圈的機制化：本案拍板 → 沉澱 → 下一案自動變成「已查證」。
- fail-open：不在 HD5 專案脈絡（往上找不到 `.claude/workflow.json`）時本節不強制。
