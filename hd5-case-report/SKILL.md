# 結案報告 ai-case-report.md（跨工單交接記憶）

> **適用對象**：主對話。在 QA 回報通過（且站上關卡通過，見 `hd5-onsite-gate`）後執行；**不由 pm／sa／實作／qa 代理執行**。
> **緣由**：案子的 spec 產物常不進版控，一張工單做完後，下一張引用它的工單無從追溯當初的最終驗收條件、改動範圍、裁定與未盡事項——
> repo 裡查不到，工單上只有原始描述。
> 解法：流程走完時產一份**固定檔名**的結案報告掛到來源工單附件；下一張工單展開引用工單時，靠這個檔名找到並下載。
> 工單本身成為唯一跨案可尋址的交接載體。
> **觸發**：通過後由主對話**自動**產出，不需使用者觸發語。上傳到工單屬對外動作：先給使用者看預覽、同意才傳；
> 使用者說「先不要上傳」就停在本地。

工單系統種類、上傳方式、權杖放哪裡等專案事實見 `AGENTS.md` 與 `.claude/workflow.json` 的 tracker；本 skill 只講方法。

---

## 一、鐵律

1. **檔名固定 `ai-case-report.md`**，位置 `AI_Service/spec/<案名>/ai-case-report.md`（案子根層，不在 pm/ qa/ 底下）。引用端靠檔名找，改名等於不存在。
2. **讀者是下一張工單的接案者／PM**，不是本案的人。每一節都要讓沒看過本案的人能據以判斷，不用縮寫、不用本案內部代號。
3. **只寫產物裡查得到的事實**：`pm/`、`sa/`、實作、`qa/` 產物、`git log`、質詢拍板紀錄、ADR、需求答覆檔。查不到的寫「無」或「未記錄」，不腦補（`hd5-no-hallucination`）。
4. **「最終驗收條件」寫實際交付版**，不是工單原文；與原文的落差要明列。引用端最常踩的坑就是拿原始描述當現況。
5. **必須帶 commit hash**（本分支的 commit 與合併節點）。spec 產物不進 repo 時，hash 是報告連回程式碼、也是引用端驗證時效的唯一橋。
6. **長度 60–150 行**。超過代表在複製產物；改成「指向」（檔名＋章節）。
7. **重傳＝更新**。工單附件通常只能新增不能刪除，引用端取上傳時間最新的一份；UAT 後結論有變、或合併後 hash 變動，就再傳一次，不要改檔名。
8. **不含機密**：連線字串、帳密、存取權杖、客戶個資、內網主機明細一律不寫。報告會跟著工單被任何有工單權限的人看到。

## 二、產出時機與流程

1. QA 回報通過（功能／安全報告已產出、結果通過）、站上關卡 `總結：通過` 後，主對話依序：
   a. 讀：`case_spec_content/spec_*.md`（＋`related/` 若有）、PM 需求文件與答覆檔（`hd5-spec-html` 產物）、`pm/grill-*.md`、`sa/grill-*.md`、
      實作計畫與實作筆記、`qa/` 的測試計畫與測試報告（含安全報告）、`qa/onsite-gate_R{n}.md`
   b. 取 commit：`git log --oneline <開發分支>..HEAD`（或本案實際範圍）；改動檔案：`git diff --stat <開發分支>...HEAD`
   c. 依第三節範本寫 `AI_Service/spec/<案名>/ai-case-report.md`，佔位符 `{{…}}` 全部換掉
   d. 跑第六節檢查清單；有工單系統時，先預覽（確認目標工單標題正確、內容無機密）給使用者看，同意後上傳為來源工單附件
      （專案有上傳工具就用它的預覽模式＋正式模式，見 AGENTS.md；Azure DevOps 用 `hd5-workitem` 的 upload-case-report，記得帶 `-CasePath`；沒有工具就請使用者手動上傳）
   e. 回報：報告路徑、版次、工單連結（或「只產本地、未上傳：原因」）
2. **無來源工單的案子**（自主發起的 spec）：只產本地報告、不上傳，回報時說明。
3. **更新時機**：UAT 有結論變更；合併後 commit hash 變動（squash／rebase）；未盡事項轉成新工單有了編號。更新 header、第 5、6 節後重傳。
4. **不產出的情況**：QA 未通過（那是 QA 報告的事，不是結案）；使用者明確要求跳過。

## 四、上傳與權限

- 只做一件事：把檔案加為來源工單的附件。**不改動工單任何欄位**（改狀態是另一個動作，走工單閘與使用者同意）。
- 上傳前檢查：檔名固定、無殘留佔位符、必要章節齊全、commit 列有真實 hash；不過就停。
- 🔴 **上傳前也要過工單閘**（跟改待驗收同一套：獨立驗收總結通過、站上關卡總結通過且 Pass 有證據、功能地圖合格）；預覽時先看閘的結果，沒過就不上傳。特殊狀況要略過必須寫理由。（守衛：無（依工單系統而定；Azure DevOps 由 hd5-workitem 的上傳工具擋，沒裝工單工具的專案靠人））
- 上傳需要工單的**寫入**權限。寫入權杖與唯讀權杖分開放（位置見 AGENTS.md，且必須被 gitignore）。
- 沒有寫入權限的人：報告仍產在本地，回報使用者請他上傳；**不要**為了上傳去擴大唯讀權杖的權限，也不代設權杖。

## 五、引用端怎麼用它（給下一張工單的接案者／PM）

- 展開引用工單時，附件裡有 `ai-case-report.md` 就下載**最新版**到 `AI_Service/spec/<新案名>/case_spec_content/related/{工單號}/ai-case-report.md`；
  沒有就只展開描述＋附件清單（舊工單全是這種）。
- 接案回報時摘引用工單報告的：第 2 節（最終驗收條件）、第 6 節（未盡事項）、第 8 節（**真的跑那條 `git log`**，把結果寫進回報：仍有效／已有後續改動）。
- PM 讀 `related/` 當背景脈絡，**不得**當成本案驗收條件；與本案工單描述衝突時寫進「已知未確認」問使用者。
