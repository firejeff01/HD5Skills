# HD5 驗證：功能地圖＋回報口徑

> 出處：Lauren Tan（GitHub：poteto）的 `create-verification-skill`，依 HD5 流程改寫。
> 一句話：每個專案都要有一份「從沒看過這個系統的代理，冷啟動就能照著把系統開起來、像使用者一樣操作、留下證據」的文件。
> 沒有它，每次驗證都在臨場拼湊——同樣的坑（登入、權限、語系、舊版產物）每個 session 重踩一次。

本 skill 只講方法。這個專案怎麼啟動、用什麼工具驅動、測試指令是什麼，寫在該 repo 的 `AGENTS.md` 與 `AI_Service/verify/`。

適用：全角色。實作（開發中自驗）、獨立驗收（核對證據，見 hd5-review）、站上關卡（見 hd5-onsite-gate）、定期巡檢都讀同一份地圖。

---

## 一、🔴 強制（不是建議）（守衛：verify-map-check.ps1、validate-grill-gate.ps1）

`AI_Service/hd5-tools/verify-map-check.ps1` 檢查功能地圖存在且格式合格，以下呼叫點都會用到，**不合格就停**：

| 呼叫點 | 時機 | 不合格時 |
|---|---|---|
| 開工 | 接新案／開始實作之前 | 先建立或補齊功能地圖（第七節），再開工 |
| 派實作／QA 前（`validate-grill-gate.ps1 -Role <實作角色>\|qa`） | 本案標的 `@功能:<編號>` 都要在地圖裡、地圖合格 | 沒標（exit 5）、地圖不合格（6）、編號不在地圖（7）都擋 |
| 開發中自驗、站上關卡 | 開始驗之前 | 狀態標 `受阻`，不開始驗 |
| 工單閘（有工單系統時，改「待驗收」前） | 交付前 | **自動擋**，不改工單 |

站上關卡報告另跑 `verify-map-check.ps1 -Onsite <qa/onsite-gate_R{n}.md>`，檢查最新一輪報告的 A 表：

- **每一條驗收項目都要在「功能」欄對到功能地圖的編號**（＝`verify/features/` 的檔名）。
  這次動到的功能地圖裡沒有 ⇒ **先補功能檔**，閘才會過。地圖就是這樣跟著案子長大的。
- **標 Pass 的要有證據**：證據檔名（要真的存在於 `qa/onsite-gate_R{n}/` 或 `qa/`），或內嵌的 `查詢：`／`API：`／`畫面值：` 內容。
  只寫「OK」「已確認」不算。
- 只有「不適用」可以不填功能編號。

### 本案動到哪些功能：誰標、標在哪（早標，不要拖到站上關卡前才補）

曾有案子拖到站上關卡前才補功能標記，結果實作階段自驗時根本沒有地圖可照。

| 案件路線（見 hd5-workflow） | 誰標 | 標在哪 |
|---|---|---|
| 四角色 | SA | `sa/*.feature` 的 `@功能:<編號>` |
| 小問題 | SA（盤查時） | `sa/bug-analysis.md` |
| 主對話建案時已知 | 主對話 | `case_spec_content/spec_001.md` 驗收條件旁 |
| 進實作才發現動到別的功能 | 實作代理 | `pg/*.md` |

- 地圖沒有該功能 ⇒ 標的人**當下建骨架檔**（第五節的 4 節格式，不寫佔位符）；之後實作自驗、QA、站上關卡把操作步驟與地雷補完整。
- 質詢閘的 `-Skip` 只跳過質詢紀錄檢查，**功能地圖照查**。純工具修改、沒有使用者功能時才用 `-SkipFeatureMap "理由"`。

## 二、放在哪裡

功能地圖寫的是**這個專案自己的**網址、帳號、元素、地雷，所以**放在各專案，不放在本套件**：

```
AI_Service/verify/
  ├─ verify-<app>.md          驗證文件（恰好一份；6 節，見第三節）
  ├─ features/
  │   ├─ README.md            共同前提、操作慣例、證據格式（必須有）
  │   └─ <功能編號>.md         每個使用者可見功能一檔（至少 3 個；檔名＝功能編號）
  └─ scripts/                 工具腳本（體檢、劇本執行…）
```

Claude Code 另在 `.claude/skills/verify-<app>/SKILL.md` 放一個入口，內容只指向 `AI_Service/verify/`（Codex 直接讀 `AI_Service/verify/`）。

完整格式（節名、順序、檢查器的實際規則）見 `references/map-format.md`。

## 三、驗證文件 `verify-<app>.md`：6 節（順序固定，標題要含英文關鍵字）

寫給**下一個代理**，不是寫給人。每節都要是這個 repo 的真實內容，不准留佔位符（`TODO`／`TBD`／`待補`／`待填`／`<填…>`／`{{…}}`）。
指令本身含 `{{…}}`（例：`docker compose ps --format "{{.Name}}"`、Go template、Handlebars）時放進反引號或程式碼區塊，就不算佔位符。

| 節 | 要回答 | 要求 |
|---|---|---|
| `## 啟動（Launch）` | 怎麼把可驅動的實例開起來、怎麼判斷「可用」（不是只有程序有回應） | 分環境寫：**隔離實例**（可以亂點、用完即丟）／**共用測試環境**（真實資料、唯讀為主）。每個環境寫 teardown |
| `## 體檢（Doctor）` | 唯讀檢查：這個實例值不值得驅動？ | 程序在不在、**是不是這一版**（版本資訊／唯讀行為探針）、port 是不是自己的、帳號登得進去、沒有停機頁。任何怪事先跑這個 |
| `## 操作（Drive）` | 用什麼工具、真實的定位把手 | 優先穩定把手：路由、`id`／`name`、`data-*`、無障礙屬性、語系 key；不用座標和 tab 順序 |
| `## 證據（Evidence）` | 留什麼、放哪 | 見第四節 |
| `## 清理（Cleanup）` | 拆掉自己開的東西 | **只殺自己啟動的程序**（認 PID／命令列，不認程序名）；清理**永遠不刪證據** |
| `## 工具腳本（Helpers）` | 附帶的腳本與用法 | 腳本要能直接執行、用法寫在文件裡；要讀者自己反推的不算 |

可以有其他 `##` 補充節（例如「共同前提」），但這 6 節要依序出現。

## 四、證據標準

1. **走真實的使用者路徑**：從選單或網址進、按真的按鈕。不用內部 setter、測試專用端點當證明。
2. **動作和結果都要留**：不是只截最後一張。至少「操作前 → 操作 → 結果」。
3. **副作用要驗**：存檔後**重新載入**看值、匯出後**打開檔案**、送出後查資料庫／清單。畫面出現不等於成功
   ——曾有幾十個頁面的上傳鈕全部沒反應，而每頁該有的元素都在。
4. **寫入後要有一次唯讀的第二次檢視**（重新整理頁面或唯讀查詢）。
5. **dry-run／預覽模式不信名字**：用觀察確認它真的跳過了什麼。
6. **到不了就說到不了**：記下嘗試的步驟和缺的前提，標 `未驗證`；不准拿另一個入口的結果冒充。
7. 證據檔命名帶驗收項編號，例：`AC-2_存檔後重新載入.png`。
8. **判定不能自己過自己**：選單、輸入框的值在操作當下就變了，只檢查它等於期望值是假綠。要證明伺服器生效：
   先在舊頁面放標記（例如在頁面全域設一個旗標），再確認標記消失（＝換了新頁面）**且**某個可觀察結果改變（文字、列數、重新開啟讀回的值）。
9. **劇本要能重跑**：同一個實例資料會累積——名稱帶時間戳記、數量驗「增加多少」、操作「自己建的那一列」，不要寫死總數或點第一列。

建議把每個功能的操作寫成**可執行的劇本**（例：步驟檔交給 UI 自動化執行器），每一步自動記下動作、結果、網址、截圖、提示窗、主控台錯誤與 HTTP≥400——
證據就不靠人手抄，而且開發中、站上關卡、定期巡檢都能重跑同一份。

放置：開發中自驗 → `AI_Service/spec/<案名>/pg/verify/`；站上關卡 → `AI_Service/spec/<案名>/qa/onsite-gate_R{n}/`。

## 五、功能檔 `features/<編號>.md`：4 節（恰好 4 個 `##`，順序固定）

```markdown
# <功能名稱>
一段話：使用者看得到的行為是什麼。

## 子功能（Sub-features）
- 清單／查詢／新增／編輯存檔／刪除／匯出…（這個功能有哪些入口）

## 使用者怎麼到達（How to get to it）
從使用者角度：選單路徑、網址形態（含必要參數）。

## 怎麼操作（Driving it）
前提：帳號、權限、語系、需要什麼資料（第一行固定以「前提：」開頭；密碼寫「由使用者輸入」或「讀環境變數 `X`」）
1. 動作（真實把手） → 可觀察的結果
2. …
成功的終態：…（看到什麼才算過）

## 地雷（Gotchas）
- 踩過的坑與診斷特徵（附來源：案號／紀錄）
```

- 子標題用 `###`（`##` 只能是這 4 個）。
- 🔴 **登入步驟的帳密只寫來源，不寫值**：寫「帳號、密碼由使用者輸入」或「讀環境變數 `APP_TEST_PASSWORD`」（只寫名稱）。
  AI 不讀密碼檔（`.env`、含密碼的設定檔、密碼管理匯出檔）、不代打密碼；要登入時停下請使用者輸入，或用使用者事先設好的環境變數由腳本讀。
  這兩種寫法是正式內容，**不算佔位符**，也不要寫成 `<填密碼>`、`{{password}}`（那會被當成沒寫完）。（守衛：無（讀不讀密碼檔是執行當下的行為，地圖格式檢查看不出來；專案有 hook 擋讀機密檔時改標那支））
- **缺前提就讓它失敗**：環境裡沒有某個流程需要的資料 ⇒ 該流程回報 `未驗證`，原因寫進「地雷」；**絕不為了通過而把流程弄簡單**。
- 地圖列了多個入口，只驗其中一個方便的入口＝證明不完整。

## 六、在流程中的位置

```
開工 ─ verify-map-check ─┐（不合格→先建地圖）
SA（或小問題的盤查／建案）─ 標 @功能、地圖沒有就建骨架 ─ 派實作前質詢閘檢查
實作 ─ 每完成一條驗收條件 → 照地圖在【隔離實例】自驗 → 證據 pg/verify/
獨立驗收 ─ 審查者核對 pg/verify/ 的證據是否真的證明了驗收條件（hd5-review「行為證據」）
合併 → 部署測試環境 → 站上關卡 ─ 照地圖在【共用測試環境】唯讀走真實資料 → qa/onsite-gate_R{n}/（hd5-onsite-gate）
工單閘 ─ 地圖合格＋每條驗收項對到功能編號＋Pass 有證據 → 才准改待驗收
維護 ─ 站上關卡、需求方退件、巡檢發現的新坑 → 當輪寫進對應功能檔的「地雷」
```

- **隔離實例**解決的是「代理不能在共用環境亂點」：用完即丟、資料自己種。專案還沒有隔離實例時，
  `verify-<app>.md` 的 Launch 要寫明「尚無隔離實例，開發中自驗改用：…（替代做法與限制）」。
- **共用測試環境**解決的是「真實資料才出現的問題」。兩者不互相取代。

## 七、第一次建立（照 create-verification-skill 的 5 步）

1. **先讀 repo，只問看不出來的**：使用者接觸的介面、怎麼啟動、怎麼驅動（先找既有端對端測試／helper）、能擷取什麼證據、能不能隔離。
2. **寫 `verify-<app>.md` 6 節**。checkout 本身起不來就先修好或精確回報，不要在壞的基礎上寫步驟。
3. **建功能地圖**：從路由／選單挑 3～5 個最常被驗收、最常踩坑的功能起步，並寫 `features/README.md`。
4. **實際跑一次**：Launch → Doctor → 驅動地圖裡的一個功能 → 留證據 → Cleanup → 確認證據還在。
   🔴 **沒跑過的驗證文件只是草稿，不是交付物**。在替代環境跑的，要列出替代環境多做、真正目標不會做的步驟，那些步驟算未驗證。（守衛：無（是否實跑過屬事實判斷，格式檢查看不出來））
5. 之後照第六節「維護」持續長大。

## 八、回報口徑

> 這裡**不是**要你多做一輪檢查——現行模型自己就會驗，額外的「請再確認一次」只會造成過度驗證。
> 這裡規範的是「怎麼講」與「修到哪」。

### 8.1 每一條主張都要對得上一個 tool 結果

回報進度或完成前，逐條對照這個 session 裡實際跑出來的東西。

- 沒驗到的就說沒驗到；測試失敗就把輸出貼出來；跳過的步驟就說跳過。
- 已經做完且驗過的，平鋪直敘講完就好，不用加保留語。

用三種狀態標，附證據（指令＋關鍵輸出／時間戳）：

| 狀態 | 意思 |
|---|---|
| `已驗證` | 有 tool 結果可以指 |
| `已完成未驗證` | 程式改了但沒跑起來驗——**這是合法狀態** |
| `受阻` | 卡住了，寫原因 |

**隱瞞才不合法。** 環境問題導致驗不了就寫「受阻＋原因」，不要改口說「應該沒問題」。

### 8.2 判斷「有沒有效」要有對照組

只看單邊數字幾乎一定誤判。實例：某次轉換邏輯改動，近千筆資料裡「五百多筆有差異」看起來像大災難；
加一個「什麼都不做」的 no-op 版本對照後，其中絕大多數純粹是重新序列化造成的差異，真正被改的只有十幾筆。

常用的三種對照：no-op 版本、修前修後同一個探針、挑一個「不該受影響」的案例確認它沒變。

### 8.3 修 bug 先列舉同類，再動手

「修了回報的那一個、漏掉兄弟」是最常被審查者退回的原因（例：信任入口修了一種型別漏掉另一種、資料修補漏掉另一個語系的副本）。

動手前先搜出同一類的所有位置（所有呼叫點／所有語系列／所有匯入路徑／所有信任入口），
列成清單標記哪些受影響，再開始修，並為每個受影響處補一道守衛或測試。

### 8.4 🔴 發現入帳：實跑完必須交代「有沒有新發現」（守衛：無（回報結尾有沒有寫新發現屬回報紀律；專案要機械化時改標自己的守衛））

三狀態管的是「這件事驗了沒」；本節管的是「**過程中冒出來的別的問題有沒有留下來**」。

**適用時機**：任何**實跑／手驗／端對端走查／示範流程**的回報。一般輪次的例行回報不必寫。

**做法**：回報結尾強制一行，二選一——

```
新發現：{編號} {一句話}／{編號} {一句話}
新發現：0 筆
```

🔴 **「0 筆」也要寫。** 沒寫等於沒檢查，不等於沒發現——這是本行存在的唯一理由。（守衛：無（同上，屬回報紀律））

⚠ **有固定總結行的產物**（獨立驗收結果檔、站上關卡報告）：`新發現：` 放在**總結行之前**，`總結：` 永遠是最後一行。
兩條規則若寫成「總結在最後一行」與「結尾補新發現」會互相打架，曾因此有一批總結被擠到倒數第二行、閘判不到。

🔴 **不要只寫在對話裡。** 對話會被摘要、會關掉、三天後沒有人記得。
有編號的進案子的追蹤檔（HANDOFF／PROGRESS）；還沒編號的先寫進去再補號。（守衛：無（寫進哪個追蹤檔由各專案決定））

> 真實代價：曾有一次全流程實跑時發現兩個缺陷，因為當時沒有這條規定，事後再也沒進任何追蹤檔。
> 實跑的成本已經付掉了，發現卻沒有留下來。

### 8.5 🔴 錯誤升級階梯：同一個錯第二次發生，就要變成會擋人的程式（守衛：check-guard-refs.mjs）

> 來源：Lauren Tan「錯誤變規則、不變 prompt」。教訓大多寫成文字時，「已再犯 N 次」的紀錄證明文字擋不住重犯。

| 第幾次 | 要做的事 |
|---|---|
| 第一次 | 照舊：寫進對應 skill／專案紀錄，並在發現入帳（8.4）記一筆 |
| **第二次** | **必須機械化**，或在同一處寫明「為什麼無法機械化」。不准只再補一段文字、再加一個紅色警示（守衛：check-guard-refs.mjs） |
| 機械化之後 | 文字規則縮成一行，指向擋它的那支守衛／hook／測試（規則只留一個真相來源） |

**機械化選擇順序**（越前面越便宜、越早擋）：

1. **改設計讓錯誤寫不出來**（更好的 API、型別、預設值）
2. **靜態檢查**：專案的守衛腳本；既有債用 **ratchet**（只准減不准增）
3. **工具呼叫攔截**：hook（資料庫／git／部署護欄、假訊號）
4. **腳本閘**：在腳本裡擋（例：改待驗收前的工單閘）
5. **測試**：架構測試、列舉型守衛
6. 最後才是人工審查與文字提醒

**判斷「已經是第二次」**：專案紀錄／skill 裡已有同類條目、HANDOFF 有前例、或同一條紅色警示規則已經寫在兩個以上檔案。

**不適合機械化的**（屬判斷，寫明理由即可）：授權的後果端判定、回報口徑、需求方溝通這類語意判斷。

新增或修改紅色警示規則時，「守衛」欄一定填守衛名稱、「無（理由）」或「待辦（G-數字）」；`check-guard-refs.mjs` 對帳，做不到的列 `spec/guard-backlog.md`。

⚠ 機械化的守衛本身也要驗：自我測試、**mutation 驗紅**（故意違規一次，確認會紅）、用**真實資料**跑一次
（曾有驗收閘拿真實案子跑才發現幾十種檔名寫法與「總結不在最後一行」）。

## 九、常見誤區

| 誤區 | 正確 |
|---|---|
| 知識都在紀錄／規範裡了，不用另外寫 | 散在十幾處＝每次重新拼湊。地圖是「照做就能到」的一條路 |
| 寫完格式過了就算完成 | 格式檢查只看形狀；**實跑一次**才算 |
| 驗收項對不到功能，就填一個最接近的 | 補一個新功能檔。地圖就是靠這樣長大 |
| 環境缺資料，就把步驟改簡單讓它過 | 標未驗證，缺什麼寫進地雷 |
| 在共用測試環境上「試點看看」 | 會寫入的試點只能在隔離實例做；共用環境以唯讀為主（hd5-onsite-gate） |
| 「應該沒問題」 | 沒有 tool 結果就是 `已完成未驗證` 或 `受阻` |

相關：hd5-onsite-gate（站上關卡）、hd5-review（行為證據）、hd5-tdd（測試紀律）、hd5-workflow（關卡總表、工單閘）。
